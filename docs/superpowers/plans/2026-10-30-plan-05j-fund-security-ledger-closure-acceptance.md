## 一、概览

### 1.1 这一阶段做了什么

5g→5h→5i 把账务的**正向**链路做完了，但**反向**与**存量**有两处缺口：
收款账户的银行账号**明文落库**，出款单每张再存一份完整账号快照 —— 库一旦泄露，账号就跟着泄露，
而账号是唯一能直接用于资金转移的字段；结算单少纳了几笔抽佣流水时佣金少算，**平台端与商家端都看不见**。

5j 把这两处补上：

| 能力 | 落点 |
|------|------|
| 字段加密工具（AES-256-GCM + HKDF-SHA256） | `api/src/common/crypto/field-cipher.ts` |
| 独立账目密钥 + 启动校验 | `api/src/common/config/assert-payout-encryption-key.ts` |
| 收款账户改密文存储（密文 + 掩码 + 版本三列） | `merchant_payout_accounts` |
| 出款单快照改密文存储（复制**同一份**密文） | `payouts` |
| 存量数据迁移脚本（备份表 + 密钥指纹 + 版本列幂等） | `api/scripts/migrate-payout-encryption.ts` |
| 缺笔检测（平台端 + 商家端） | `settlement.service.ts` / `ledger.service.ts` / `merchant-statement.service.ts` |
| 缺笔可见（平台端列表 + 详情指引） | `platform-admin/.../settlements/` |
| 缺笔可见（商家端对账单提示） | `merchant-admin/.../statements/` |

**一句话**：账号不再明文落库；佣金笔数与流水对不上时，两端都看得见。

### 1.2 结论

- **浏览器手测 6 步全部实测通过**（另加 3 项额外验证）；
- **失败注入 F1–F11 逐条跑完，11 条全部有牙齿**（无一挂 0 条）；
- 两轮独立审查（规格符合性 → 代码质量）各抓到 **1 处必须修的真缺陷**，
  另有 3 处测试区分力缺口、1 处既有的界面缺口被补上；
- 手测**翻出 1 个既有的界面缺口**（出款单详情页从不显示收款账户），
  **当场补上**并说明为什么 5j 之后它变得更要紧；
- 全量测试：api 单测 **519**、api e2e **608**（33 套）、merchant-admin **394**（27 文件）、
  platform-admin **364**（15 文件），全绿。

## 二、关键设计决策

### 2.1 字段加密，密文列**改名**而不是保留旧名

`accountNo` → `accountNoCipher`、`snapshotAccountNo` → `snapshotAccountNoCipher`。
列名带 `Cipher` 后缀是为了自解释 —— 保留 `accountNo` 却让它装密文，只靠注释说明，
下一个读代码的人容易误解。

⚠️ 迁移用 `RENAME COLUMN` 而不是「加新列 + 删旧列」：老代码读旧列名会**立刻报「列不存在」**，
不会静默读错 —— 停机窗口内不会出现「新旧代码同时跑」的危险状态。

### 2.2 幂等判定靠**版本列**，不靠「能不能解密」

`encryptionVersion`（0 = 尚未加密，1 = 已加密）是「这行加密过没有」的**权威依据**。

⚠️ 「解不开」有两种完全不同的原因：**还没加密**与**密钥配错**。用启发式判断的话，
密钥配错时会把所有行当成「明文」，**用错密钥加密并覆盖原文，而原文被覆盖后不可恢复**。

**这条不是理论 —— 失败注入 F11 实测复现了**：改用解密启发式 + 错密钥 + `--force`，
脚本把 **65 行已加密数据用错密钥重新加密覆盖**，此后正确密钥**永久解不开**
（复验：正确密钥解=FAIL / 错误密钥解=OK）。

### 2.3 展示路径**全程不解密**

展示路径读**预存的掩码串列**，不解密：
- `PayoutAccountService.toView()` → `maskedAccountNo`
- `PayoutService.toView()` → `maskedSnapshotAccountNo`

解密点全仓只有两处：`payout-execution.service.ts`（打款）与迁移脚本。
展示路径一旦解密，护栏 X14（响应永不含完整账号）就有洞了。

⚠️ 掩码串**必须单独存**：密文长度 ≠ 明文长度，而掩码要按明文长度打星 → 不解密就还原不出掩码。

### 2.4 户名与开户行**有意保持明文**

账号是唯一能直接用于资金转移的字段，户名与开户行是卡面上就印着的公开信息。
⚠️ 这句话留在 schema 注释里 —— 否则下一个读代码的人会以为漏做了，进而「顺手补上」把设计改乱。

### 2.5 快照复制**同一份密文**，不重新加密

`apply` 与 `approve` 都是直接复制 `account.accountNoCipher`，**版本号一起复制**。
重新加密会得到不同的密文（随机 iv），而「快照 = 审批那一刻的那一份」要求复制同一份密文。

⚠️ 版本号必须跟着密文一起复制 —— 否则会出现「密文是新的、版本号是 0」的错配。

### 2.6 写路径也要查加密版本（审查抓到的真缺陷）

读路径遇到 `encryptionVersion = 0` 会抛错，但**写路径原本漏了这道闸**：
账户行未迁移时 `accountNoCipher` 里装的是明文，`apply` 抄进快照就是**明文落库**，
而且打款必然抛错 → 出款单卡在 `PROCESSING` 反复重试。

现在 `apply` 与 `approve` 都在建单前拒掉未迁移的账户 —— 宁可不建单，
也不要造出一张注定打不出钱的单。

### 2.7 缺笔只比**笔数**

`missingEntryCount` = 当期真实流水笔数 − 结算单纳入笔数。
抽佣流水是 **append-only**（全仓无 `update` / `updateMany` / `upsert`），
笔数没变 ⇒ 纳入的集合没变 ⇒ 金额也没变。

⚠️ 若将来流水变得可变（可改金额 / 可改归期），这里必须改成比金额之和。

### 2.8 归期按流水自己的 `occurredAt`，不用账单的 `periodStart`

流水的归期是 `occurredAt`（支付取 `paidAt`、退款取 `refundedAt`），账单的周期是 `periodStart` ——
两者不是一回事（跨期回填的流水归期在退款期，不在原期）。

⚠️ 平台端列表页是**跨租户**的 → 分组键必须带 `tenantId`，漏了会跨租户串数。

### 2.9 「还没结算」≠「缺笔」

商家端**没有结算单的期，`missingEntryCount` 恒为 0**。
直接相减会把「这一期还没结算」误标成「结算单缺笔」
（与 5i 的口径一致：没有结算单 → `commissionAmount` 恒为 `null`，不是 0）。

## 三、失败注入（F1–F11）

做法：**脚本化注入** —— 改一处 → 跑最小定向测试 → 确认目标用例挂 → 还原 → **校验还原**（哈希 + `git diff --stat`）。
⚠️ 注入**独占**执行，不与全量测试并发。

| # | 注入点 | 锚点 | 目标用例 | 挂的条数 | 结果 |
|---|--------|------|---------|---------|------|
| F1 | 写入时不加密（存明文） | `payout-account.service.ts:126` | create 落库的是密文 | 1 | ✅ 符合预期 |
| F2 | 明文写进 `...Cipher` 列（update 分支） | `payout-account.service.ts:97` | 已有账户 → 走 updateMany 分支 | 1 | ✅ 符合预期 |
| F3a | 展示路径返回明文（账户） | `payout-account.service.ts:149` | X14 断言 | 9 | ✅ 符合预期 |
| F3b | 展示路径返回明文（出款单） | `payout.service.ts:1255` | 完整账号绝不进 API 响应 | 1 | ✅ 符合预期 |
| F4 | 打款路径不解密 | `payout-execution.service.ts:133` | 渠道收到的账号是明文 | 2 | ✅ 符合预期 |
| F5 | 缺笔判定的不等号改成 `<=` | `settlement.service.ts:564` + `:1037` | 缺笔数判定 | 8 | ✅ 符合预期 |

| F8 | 商家端不返回缺笔字段 | `merchant-statement.service.ts:322` | 商家端提示用例 | 3 | ✅ 符合预期 |
| F9 | 平台端缺笔标识恒为 0 | `settlement.service.ts:564` + `:1037` | 平台端缺笔用例 | 3 | ✅ 符合预期 |
| F10 | 版本 0 按明文兜底（不抛错） | `payout-cipher.service.ts:67` | 未迁移行的读取用例 | 1 | ✅ 符合预期 |
| F11 | 迁移脚本靠「能不能解密」判幂等 | `scripts/migrate-payout-encryption.ts:76` | 密钥配错时拒绝写库 | 数据被覆盖 | ✅ **符合预期**（见下） |

**没有一条挂 0 条。**

### 3.1 F11 的实测结论（本次最有价值的一条）

| 场景 | 脚本行为 |
|------|---------|
| **未改坏的脚本** + 错密钥 + `--force` | 「待迁移：账户 0 行 → 无需迁移」，**拒绝写库**，已加密的行一字节未动 ✅ |
| **改用解密启发式** + 错密钥 + `--force` | 「迁移完成：账户 65 行、出款单快照 53 行」→ **把全部 65 行已加密数据用错密钥重新加密覆盖**，此后正确密钥永久解不开 |

这就是版本列存在的理由 —— **幂等判定不能建立在「能不能解密」上**。

（测试在 `ecommerce_test` 库上做的，事后已逐行还原并复验：剩余备份表 0 张、正确密钥可解。）

### 3.2 注入暴露的护栏弱点（已处理）

1. **`PayoutCipherService` 原本没有独立单测文件** —— `decryptVersioned` 的版本 0 分支只被
   `payout-execution.service.spec.ts` 的一条用例间接覆盖。那条用例一旦被删，「版本 0 按明文兜底」
   就会**静默通过** → **已补 `payout-cipher.service.spec.ts`（12 条）**，
   直接覆盖版本 0 / 1 / 2 三条分支，且断言版本 0 与版本 2 的错误文案**不同**。
2. **F3b 暴露「结构性而非断言性」的护栏** —— `PayoutService` 的构造函数**根本没注入** `PayoutCipherService`
   → 展示路径**没有能力**解密。这条护栏靠的是「类里没有密钥」这一事实，不是靠 X14 断言。
   断言仍然有效（注入后照样挂），但若将来有人给 `PayoutService` 注入 cipher，靠的就只剩断言。
3. **单张路径与批量路径的护栏强度不对称** —— F6 注入后，批量路径的「列表页一次查完」断言
   （`commissionEntry.findMany` 只调 1 次）会连带抓住「查询源被换掉」的注入。
   若只保留语义断言而不保留「只查一次」那条，批量侧的同类变异可能漏网。
4. **双路径重复实现** —— `missingEntryCountOf` 与 `missingEntryCounts` 各写一遍
   `Math.max(0, actual - entryCount)`。两处都被测试覆盖，但重复实现带来长期漂移风险
   → 已补「`periodEnd` 被改宽时单张路径与批量路径必须一致」那条用例专门盯这个。

## 四、浏览器手测

环境：商家端 `http://localhost:3002`、平台端 `http://localhost:3003`，
浏览器用本机 `ego lite`（全程未抢前台，任务结束关闭标签页）。
账号 `owner@demo.platform.test / Demo12345!`、`admin@platform.test / Admin12345!`。

手测前用 SQL 造了两期的流水（订单用无流水记录的既有订单，避免唯一约束冲突）：

| 期 | 货款流水 | 抽佣流水 | 结算单 |
|----|---------|---------|--------|

### 4.3 第 4 步的证据边界（如实记录）

假出款网关**只有 `POST /pay/fake-payout/fail-next` 一个端点，没有查询「实际收到了什么」的接口**
（`received` 是进程内的 `Map`），也不打日志。

所以手测层面能拿到的证据是：
- 打款**成功**（`PAID` + 日志「出款已打款」）—— 打款路径必须先解密拿到明文才能调渠道，
  解密失败会抛错、单子不会变 `PAID`；
- 快照密文与账户行密文**逐字相同** + 掩码尾号 `1234` 一致。

**「渠道收到的就是完整明文账号」这条更强的断言由 e2e 的 X2b 用例守着** ——
`expect(received!.account.accountNo).toBe('6225880000000000')`（假网关按 `referenceId` 记录实际发出的请求）。
那条断言在 5h-2 就已存在，5j 没有削弱它（快照改成密文后，worker 解密再传给渠道）。

### 4.4 额外验证（3 项）

- **「可修」分支**（2026-07：已确认、无出款单引用）→ 详情给
  「本期尚无出款单引用，可先「取消确认」再「重算」，重算会把当期的流水重新纳入。」，
  且页面上**确实有「取消确认」按钮** —— 指引与实际能走的路一致。
- **「不可修」分支**（2026-08：已出款、被出款单引用）→ 详情给「需走调账流程」。
- **审批时快照未重新加密** → `approve` 之后 `snapshotAccountNoCipher` 与申请时**逐字相同**
  （复制而非重新加密）。

### 4.5 手测翻出的缺口（已补）

**平台端出款单详情页从不显示收款账户。**

- 后端 `PayoutService.toView()` 一直返回 `maskedSnapshotAccountNo` / `snapshotAccountName` / `snapshotBankName`，
  但 `platform-admin` **从来没有渲染过它们**（5h-2 交付时就没有，**不是 5j 引入的**）。
- 规格的手测项「平台端出款单显示掩码账号」因此落不了地。
- ⚠️ **5j 之后它变得更要紧**：以前运营可以查库看**明文**账号来核对收款账户，
  现在库里只有密文，**掩码串成了唯一能核对的东西**，而界面上连掩码串都不显示。
- **已补**：详情页在「申请时预估」之后显示「收款账户：招商银行 \*\*\*\*\*\*\*\*\*\*\*\*1234（张三）」；
  三个字段可能为 `null`（老数据没快照）→ `describePayoutAccount` 返回 `null` → **整行不渲染**
  （不用「—」占位，避免让超管以为「开户行不知道」而实际是「这张单没有快照」）。

### 4.6 手测后的清理

- 手测数据已按外键依赖顺序删干净（`payout_entries` → `payouts` → `settlement_statement_entries`
  → `settlement_statements` → `commission_entries` → `merchant_receipts`）→ 复查**全部为 0 行残留**；
- `infra/docker-compose.yml` 的临时开关（`NODE_ENV: development` + `FAKE_PAYOUT_ENABLED: 'true'`）
  **已 `git checkout --` 还原**，api 用 production 配置重启后 healthy；
- ⚠️ `docker exec` 全部带 `-i`（5j 实测踩过：缺 `-i` 时 heredoc 传不进去，
  **退出码 0 但一行都没删**）。

## 五、已知差异与遗留

| # | 事项 | 说明 |
|---|------|------|
| 1 | **商家端看不到收款账户** | 5j 只补了平台端（规格手测项只提平台端）。商家端出款列表/详情同样不显示掩码账号 —— 商家想确认「钱打给谁」得问平台。**建议下一阶段补**。 |
| 2 | **商家端与平台端的「纳入笔数」来源不同** | 平台端用结算单的 `entryCount` **快照列**，商家端用**实际存在的关联行数**。正常数据下两者相等（`recalculate` 会同时更新两者）；只有「关联行指向已不存在的流水」这种脏数据下不等。**有意保留的差异**，未统一。 |
| 3 | **「PayoutService 没注入 cipher」是结构性护栏** | 展示路径没有能力解密 —— 靠的是「类里没有密钥」这一事实，不是靠 X14 断言。见 §3.2 第 2 条。 |
| 4 | **缺笔的双路径重复实现** | `missingEntryCountOf` 与 `missingEntryCounts` 各写一遍 `Math.max(0, actual - entryCount)`。已用一条专门的用例盯住两者的一致性，但重复实现本身是长期漂移风险。 |
| 5 | **本地 `.env` 与 compose 的密钥必须一致** | `api/.env` 的 `PAYOUT_ACCOUNT_ENCRYPTION_KEY` 与 `infra/docker-compose.yml` 的固定值**逐字一致**。本地跑迁移脚本用的是 `.env` 的值，容器里的应用用的是 compose 的值 —— **不一致的话，脚本加密的数据容器永远解不开**。⚠️ `api/.env` 不入库，靠纪律保证；`JWT_SECRET` 本来就不一致（对 JWT 无害，对账目密钥是致命的）。 |
| 6 | **密钥轮换后已打款的快照永久解不开** | 这是设计的代价，不是缺陷。密钥必须像 `JWT_SECRET` 一样固定并备份好。 |
| 7 | **掩码串会泄露账号长度** | 掩码串按明文长度打星 → 长度可见。**现状 API 返回的就是掩码串**，不是新增泄露面。 |
| 8 | **迁移脚本的备份表会留在库里** | `merchant_payout_accounts_backup_<时间戳>` / `payouts_backup_<时间戳>`。有意保留（迁移出问题可恢复），但会一直占空间，需要人工清理。 |
| 9 | **开发库残留** | 迁移脚本跑完后，备份表里仍有明文账号（`6225880000001234`）。业务表已无明文。 |
| 10 | **e2e 的读路径抛错会让出款单停在 `PROCESSING`** | 解密在 worker 的 try/catch **之外** → 抛错后单子既不 `PAID` 也不 `FAILED`。写路径闸已堵住「明文快照落库」这个触发源，但「版本不认识」等其它异常仍会卡住。属于卡死告警兜底的话题，不在本阶段范围。 |
| 11 | 5h-1 遗留的两条概率性 flaky | `payment-compensation`「扫描 A…」/ `payout`「P7…」概率性挂（本进程 BullMQ worker 抢走测试自己入队的 job）。本次全量跑 608 条全过，未触发。 |
| 12 | 平台端与商家端共用 `localhost` cookie | 两端 cookie 同名同域 → 交替登录会互顶。本次靠「分端登录、每端做完再换」解决。 |

## 一、概览

### 1.1 这一阶段做了什么

5h-1 把出款做到了「**已审批**」——钱还没打出去。5h-2 补上真正打钱的那一段：

| 能力 | 落点 |
|------|------|
| 审批后**自动打款**（worker 调渠道） | `PayoutWorker` + `PayoutExecutionService` |
| 状态机 `APPROVED → PROCESSING → PAID / FAILED` | `payout-execution.service.ts` |
| 失败**重试 3 次**（30s / 60s 退避） | `PayoutWorker.handleFailure` |
| 卡死兜底扫描（`APPROVED` 救援 + `PROCESSING` 只告警） | `PayoutScanScheduler` + `scanStuck` |
| **补差出款**（正常单已结清后又回填的货款） | `payout.service.ts` 的 `apply` / `approve` 分 `kind` 两条路 |
| 假出款网关（本地开发用） | `FakePayoutProvider` + `FakePayoutController` |

## 二、关键设计决策（实施期确认过的口径）

### 2.1 佣金不变量

**同一期所有出款单的 `commissionAmount` 之和 = 该期结算单的 `netAmount`。**

- 正常单：佣金 = 结算单的 `netAmount`（整期一次性扣完）；
- 补差单：佣金 **恒为 0**（这一期不再扣佣）。

**代价（如实记录）**：平台在「回填货款」上**没收佣**（漏结佣金，见 §六·L54）。
这是本单口径下的必然结果 —— 结算单的 `netAmount` 已在正常单出款时一次性扣光。

### 2.2 「本单口径」vs「全局口径」

补差单审批时重算金额，**必须用本单口径**：

- 本单口径 = 「本单已占用的流水」∪「该期未被**其他**单占用的流水」；
- 全局口径 = 「该期未被**任何**单占用的流水」。

用全局口径 → 本单自己纳入的流水被当成「未纳入」→ **金额归零** → 审批直接 409。
（失败注入 Y19 实测：注入后 X16 用例挂掉，正是这个形状。）

### 2.3 三处「双重防线」（实测挂 0 条的原因）

| 防线 A | 防线 B | 单去掉 A 能否观测 |
|--------|--------|-----------------|
| `markPaid` 的 `status: PROCESSING` 条件 | `claimForExecution` 的 `status: APPROVED` 条件 | ❌ 不能（抢不到单就轮不到 `markPaid`） |
| `markPaid` 的 `kind === 'NORMAL'` 判断 | 结算单更新的 `status: CONFIRMED` 条件 | ❌ 不能（结算单早已是 `PAID`，条件更新影响 0 行） |
| `availablePeriods` 的 `kind` 过滤 | `PAID` 的正常单**也是**活跃单 | ❌ 不能（正常单永远存在，捞不到错位） |

**这三条不是缺陷，是「一条业务规则配了两道闸」**。已在 §四·4.3 记录，不作为遗留项。

### 4.3 ⚠️ 三类「挂 0 条」的翻案（**不是护栏缺失**）

**这一节是本阶段最重要的一条经验** —— 5g 的教训在这里第三次应验。

#### ① Y5 / Y6：双重防线（护栏在，但测不出来）

- **Y5**（`markPaid` 去掉 `status: PROCESSING`）→ 20 条全过。
  **原因**：真正的防线是**上游**的 `claimForExecution`（`where` 带 `status: APPROVED`）——
  单已是 `PAID` 时**根本抢不到**，`markPaid` 轮不到被调用。
  「已 `PAID` 的单不能被撤回 / 拒绝」那两条用例走的是 `cancel` / `reject`
  的条件更新，与 `markPaid` 无关。
- **Y6**（`markPaid` 去掉 `kind === 'NORMAL'`）→ 20 条全过。
  **原因**：补差单打款时结算单**早已是 `PAID`** → 结算单更新的条件
  `status: CONFIRMED` 匹配不上 → `updateMany` 影响 0 行 → 状态不会变。
  两道闸任去其一，结果都一样。

**结论**：这两条不是「护栏没有牙齿」，是**一条业务规则配了两道闸**，
e2e 验证的是**结果**而不是「哪一道闸生效」。**如实记录，不作为缺陷。**

#### ② Y16 的原注入点在本数据模型下不可观测

原计划是「`availablePeriods` 的活跃单查询去掉 `kind` 条件」。实测挂 0 条，
原因是**补差单必须依附于一张 `PAID` 的正常单**（否则走正常路径），
而 `PAID` 的正常单**也是活跃单**（`notIn` 不含 `PAID`）→
「该期只有补差单、没有正常单」这个形状**不存在** → 查询不可能错位。

**改用的注入点**：`availablePeriods` 的活跃单查询**排除 `PAID`**
（等价于 5h-2 之前的老口径）→ 正常单已结清时补差入口消失 → 挂 1 条 ✅。

#### ③ Y19 是**我的注入写错了**（不是护栏的问题）

第一版注入把「本单口径」改成：

```ts
(receipt) => ownIds.size >= 0 && !otherIds.has(receipt.id)
```

`ownIds.size >= 0` 恒真 → 范围仍是「未被**其他**单占用的」→ **根本没改成全局口径**
→ 挂 0 条是**必然**的。

改成真正的全局口径：

```ts
(receipt) => !ownIds.has(receipt.id) && !otherIds.has(receipt.id)
```

→ 本单纳入的流水被排除 → 金额归零 → 审批 409 → **挂 2 条** ✅。

⚠️ **教训**：注入写错和护栏没牙齿长得**一模一样**（都是「挂 0 条」）。
必须先确认「替换真的生效了、且语义确实是那个意思」，再下结论。

#### ④ 复验 5h-1 的 F9-b 时，又踩了一次「注入写错」

5h-1 的遗留项 F9-b（「商家撤回避绕租户过滤」注入挂 0 条）在本阶段已随
P9 拆成两个独立用例而修好。为确认它真的有了牙齿，重新做了一次注入：

```ts
// ⚠️ 第一版：回调是**同步函数**
await tenantContext.run(platformScope(), () =>
  this.prisma.payout.findFirst({ where: { id: payoutId } }),
);
```

→ **挂 0 条**。原因是项目注释里写明的那条约束（`tenant-context.ts`）：

> 所有 `tenantContext.run(...)` 的回调**必须是 async 函数**。
> Prisma 6 的 query 返回 PrismaPromise（thenable 而非原生 Promise），

改成 `async () =>` 后 → **挂 1 条**（「P9：商家不能撤回别家的出款单（DELETE 越权）」）✅

## 五、发现并修复的缺陷（实施期）

| # | 缺陷 | 影响 | 修法 |
|---|------|------|------|
| 1 | `PayoutStatus` 枚举漏了 `PROCESSING` | 迁移跑不起来 | 单独一个迁移文件补枚举（`20261029110000_add_processing_status`）|
| 2 | 兜底扫描**周期任务从未注册** | `APPROVED` 救援是死代码 —— 审批后入队失败 → 单子永远停在 `APPROVED` | 补 `PayoutScanScheduler`（照 `CompensationService` 的形态，5 分钟一次）|
| 3 | `approve` 不同步 `payout_entries` | 审批纳入的新流水没被占用 → 商家能再申请补差单**把同一笔再打一次**（**重复打款**）| 同事务里 `deleteMany` + `createMany` |
| 4 | 救援判据少了 `attemptCount = 0` | 救援 job 与重试 job 抢跑 → 3 次预算几秒内烧光 | 判据加 `attemptCount = 0` |
| 5 | 重试的 jobId 用「这一轮」的 `attemptCount` | 与首次入队的 jobId 撞了 → BullMQ **静默忽略** → **重试从未发生** | 改用「下一轮」`nextAttempt + 1` |
| 6 | `apply` 的幂等分支把 `PAID` 的正常单也当活跃单 | **补差路径不可达** —— 商家看到「可申请补差」，点了却拿回那张已出款的旧单 | 收窄为 `existingNormal.status !== PAID` |
| 7 | 5h-1 的两条 P7 e2e 挂 | worker 现在真的在跑，状态会变 `APPROVED → PROCESSING`，5h-1 的「状态必须停在 `APPROVED`」前提作废 | 放宽为「不是 `REQUESTED` / 不是 `CANCELLED`」|
| 8 | 5h-1 的 P9 用例把 GET 与 DELETE 的断言挤在一个 `it` 里 | GET 的断言先失败 → DELETE **轮不到执行** → 「撤回越权被挡住」这条护栏**实际没被验证**（5h-1 遗留的 F9-b）| 拆成两个独立用例，并复验注入挂 1 条（§4.3·④）|

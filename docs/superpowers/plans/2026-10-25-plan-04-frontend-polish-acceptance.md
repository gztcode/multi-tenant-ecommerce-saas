| 位置 | 内容 |
|------|------|
| `storefront/vitest.config.ts` | `include` 扩到 `{ts,tsx}`；**根级**加 `esbuild: { jsx: 'automatic' }`；全局环境保持 `node` |

| `storefront/test/components/theme/theme-watcher.test.tsx` | 主题轮询与客户端注入（7 条） |

**三个关键的坑（都踩过了，写在这里免得下次重蹈）**：

1. **`esbuild.jsx` 必须加在配置的根级**——加在 `test` 下面不生效（esbuild 是 Vite 根级选项）。
   不加它，所有组件测试报 `ReferenceError: React is not defined`
   （`tsconfig.json` 的 `"jsx": "preserve"` 是给 Next 的 SWC 用的，esbuild 不读）。
2. **必须显式 `cleanup()`**——本项目 Vitest 配置 `globals: false` → 全局 `afterEach` 不存在
   → RTL v16 的自动 cleanup 根本不注册 → DOM 跨用例累积 → 从第 2 条用例起报
   `Found multiple elements with the role "button"`。
3. **逐文件 `// @vitest-environment jsdom` 优先于全局配置**——所以失败注入 #1 的形态必须是
   「删掉某个文件的首行注释」，**不是**「把全局 `environment` 改成 `node`」
   （后者不会生效，实测确认）。

### 场景 2：多标签页「先后」刷新竞态（设计文档 L20）

**结果：⚠️ **复现了，而且比设计文档设想的更容易触发****

设计文档预期的是「先让 A 刷新成功，再让 B 触发刷新」这个**需要等令牌过期**的序列。
**实测不需要等到过期**——流程是：

1. 标签页 A（`p1`）已登录商家后台，令牌在 A 刚刷新过一轮。
2. **新开标签页 B**（`p3`，同一个浏览器 → 共享 cookie），直接访问 `http://localhost:3016/`。
3. B 的会话读取带着**旧 cookie 里的旧 refreshToken** 去刷新 →
   那枚令牌在 A 刷新时已被轮换 → 后端判成「真正的重放」→ `revokeTokenFamily` **吊销全族**。

**实测证据**（`refresh_tokens` 表）：

```
 revokedReason |         createdAt          |         revokedAt
---------------+---------------------------+---------------------------
 REPLAY        | 2026-10-25 03:11:17.934   | 2026-10-25 03:11:45.934
 REPLAY        | 2026-10-25 03:10:08.136   | 2026-10-25 03:11:45.934
 REPLAY        | 2026-10-25 03:09:59.565   | 2026-10-25 03:11:45.934
 REPLAY        | 2026-10-25 03:09:13.136   | 2026-10-25 03:11:45.934
 REPLAY        | 2026-10-25 03:08:45.952   | 2026-10-25 03:11:45.934
 REPLAY        | 2026-10-25 03:06:42.200   | 2026-10-25 03:11:45.934
```

- 该用户的 **9 枚 refreshToken 全部**在**同一毫秒**（03:11:45.934）被标成 `REPLAY`。
- **标签页 A 也被踢下线**：`p1` 刷新后跳到 `http://localhost:3016/login`，页面显示「商家后台登录」。

**这比设计文档的描述更严重**：设计文档 §7 遗留项 13 写的是「在宽限期机制落地前，
多标签页并发使用商家后台**存在**被全设备踢下线的风险」——实测表明这**不是「并发」，
而是「顺序」**：只要**开了第二个标签页**就会触发，不需要任何并发压力。
**商家只要同时开两个后台标签页，就会被踢出登录。** 这是本轮手测挖出的**最严重的问题**。

**本阶段不修后端**（设计如此），如实记为遗留项（§六 遗留项 4）。

> 📌 **后续补记**：该问题在验收结束后**已修复**（提交 `8545635`）。
> **根因的准确描述**（RSC 分支丢弃 `Set-Cookie`）与**修复的边界**
> （同源多标签页已解决；多浏览器 / 多设备仍需后端宽限期）见 **§六 遗留项 4**。

### 账目说明

**① 失败注入 #6 与 #8 为什么没抓到 —— 这是本次验收最重要的发现之一。**

两个注入都在 `merchant-admin/src/auth.ts` 的 `jwt` 回调里：

```ts

if (false) { return token; }              // ← 注入后

// #8：刷新失败分支改成「保留旧令牌」
return token;                              // ← 注入后
```

**注入确实生效了**（编译通过、`git diff` 看得见改动），但 **75 条测试全绿**
（这轮失败注入是在「阶段 4 主体」的数字下做的；`8545635` 之后该数字是 82，
但 `auth.ts` 的这层**依然零覆盖**——`session-sync` 的 7 条用例测的是多标签页协调，
不是 `jwt` 回调本身）。

**根因**：`auth.ts` **没法进单元测试**——它顶层就调 `NextAuth({...})`，
import 它就会初始化 next-auth 的整个依赖图（含 `server-only`），
在 Vitest 的 node 环境里直接报 `Cannot find module 'next/server'`。
设计文档 §4.2.2 已经写明了这一点，**实施时把判据抽成了纯函数**
（`shouldInvalidateSession`）来测——但**只抽走了「要不要作废」的判据**，
**`jwt` 回调本身（什么时候刷新、刷完怎么写回 token）依然零覆盖**。

后果很具体：

- **护栏 3（L1，可被利用的漏洞）**：「accessToken 过期时刷新」这条逻辑**被删掉也不会有任何测试挂**。
  本阶段花大力气做的令牌刷新，**只有手测在守着**。
- **护栏 5（L1 / L18）**：「刷新失败作废会话」里的**「作废」那一步**同样零覆盖
  （`shouldInvalidateSession` 只覆盖了判据，没覆盖「判据为真之后真的把会话作废了」）。
  另外把 `layout.tsx` 的 `!session?.accessToken` 退回成 `!session`、
  把 `session` 回调的 `?? ''` 去掉，**同样 75 条全绿**（同上，`8545635` 之后是 82 条，
  这一层**依然零覆盖**）。

**这不是「测试写错了」，是「这一层压根没测」。** 如实记为遗留项（§六 遗留项 6）。

## 六、已知遗留项

**诚实地列出来：哪些没测到、哪些没覆盖、哪些是刻意的取舍。**

### 本阶段新发现的

1. **字体 token 在服务端就无效 —— 商家改字体，前台从来就没生效过**（实测确认，见 §三 场景 10）。

   **本阶段新发现，不是阶段 4 引入的**（服务端注入的那份从来就不生效），
   但阶段 4 实施时把这件事彻底查清楚了。

   根因有两条，叠加起来：
   - `globals.css` 的 `--font-sans: var(--font-sans)` 是**自引用**，
     编译产物落在 `@layer theme{:host,:root{--font-sans:var(--font-sans)}}`，
     是个**循环引用** → **计算值阶段就无效**（不是「优先级不够」，是「解析不出值」）。
   - `--font-geist-sans` 由 `next/font` 挂在 **`<body>`** 上（`layout.tsx` 的
     `__variable_*` 类），**root 作用域看不到**。

   实测：前台 `--font-sans` 计算值是 `""`，实际渲染字体是 `"PingFang SC"`（系统默认）。
   **结论：商家在后台改「正文字体 / 等宽字体」，前台从来就没生效过。**

   客户端的 `ThemeWatcher` **已经正确排除了**
   `fontSans` / `fontMono`（并有专门的组件测试断言）。

   **要修需要两端一起改**：把 `--font-geist-sans` 也挂到 `<html>` 上，
   **并且**去掉 `globals.css` 里的自引用。
   在此之前，**商家后台的「正文字体 / 等宽字体」两个输入框是摆设**。

2. **商家可编辑的分组标量（字阶 / 间距 / 阴影 / 字重）在前台没有消费者**（实测确认，见 §三）。

   **本阶段新发现，不是阶段 4 引入的**（前端从阶段 2b 起就在写这四组变量，
   但 CSS 侧一直没有消费者）。

   实测：把「字阶 → 正文」从 `1rem` 改成 `2.5rem` 并保存 → 前台的 `--text-base`
   **确实变成了 `2.5rem`**（客户端写了），但**页面上实际渲染出来的 `<p>` 的 font-size
   仍是 `14px`** —— 一个字都没变大。

   根因在 **CSS 侧没接线**：`globals.css` 的 `@theme inline` 只映射 colors / radius / fonts，
   **字阶 / 间距 / 阴影 / 字重这四组没有任何一条规则去用它们**。
   **要修**：在 `@theme inline` 里补上映射，或把这些变量接到具体的 utility class 上。

   ⚠️ 本阶段的客户端**保留写入**这四组变量（对齐服务端 `buildThemeCss` 的行为，成本为零），
   将来 CSS 侧接上消费者时不需要再改客户端。

3. **商家后台的「主题实时预览」本阶段没做**（设计文档 §一 的 4a）。

   实测：商家在后台改主色并保存后，**后台页面里没有任何东西变色** ——
   商家**自己都看不到变化**，只能切到另一个标签页看前台。
   这正是设计文档 §7 遗留项 10 描述的场景。**本阶段只解决了它的另一半**（4b，前台访客的实时生效）。

   **要修**：商家后台的主题编辑页需要一份**预览 iframe / 预览容器**，
   自己调 `/public/theme`（或直接用编辑中的草稿值）渲染一份样式，与后台布局解耦。

4. **多标签页的「先后」刷新竞态：⚠️ 已缓解（同源多标签页），但仍需后端根治**

   #### 4.1 验收当时的实测结论（现象未变，根因已修正）

   设计文档设想的是「A 刷新成功后再让 B 触发刷新」（需要等令牌过期）。
   **实测是「新开第二个标签页」就会触发** —— 实测：同一毫秒内该用户的
   **9 枚 refreshToken 全部被标成 `REPLAY`**，
   **原本已登录的标签页 A 也被踢到登录页**。

   **商家只要同时开两个后台标签页，就会被踢出登录** —— 这不是「存在风险」，
   是「一定会发生」。

   #### 4.2 根因的准确描述（验收当时记错了方向，修正如下）

   > ⚠️ **验收当时的归因（「cookie 里的旧令牌」）方向对，但没说清机制，
   > 而且有一处事实错误**——当时以为刷新令牌存在「浏览器 JS 存储」里，
   > 实际上它在 **HttpOnly cookie** 里，**跨标签页共享**。
   > 真正的破口在**服务端**。

   真实的失效链（提交 `8545635` 核实）：

   1. 刷新令牌在 **HttpOnly cookie**（NextAuth 的 `authjs.session-token`）里，
      **cookie jar 跨标签页共享** → 每个标签页拿到的都是**同一枚**旧令牌 T0。
   2. 标签页 A 的服务端读会话发现 accessToken 过期 → 调后端刷新 →
      T0 被标 `ROTATED`，后端下发新令牌 T1。
   3. ⚠️ **但 T1 从来没到过浏览器**：
      **Server Component 里的 `await auth()` 走 next-auth 的 RSC 分支，
      那条分支只取响应体（`parseSessionResponse`），把 `Set-Cookie` 丢掉了**；
      而 Next.js 又只允许在 Server Action 或 Route Handler 里写 cookie，
      Server Component 渲染阶段写会抛 `ReadonlyRequestCookiesError`。
      **于是「服务端轮换了 T0→T1，浏览器永远拿不到新令牌」。**
   4. 浏览器手里永远攥着那枚**已经作废的 T0**。标签页 B（或 A 的下一次读会话）
      拿 T0 去刷新 → 后端 `isConcurrentRace` 判否（轮换时间早于请求起始时间）→
      落到「③ 真正的重放」→ `revokeTokenFamily` → **吊销该用户全部设备的登录**。

   **一句话**：不是「标签页之间互相踩」，是
   **「刷新结果送不回浏览器」——每读一次会话就把令牌往作废的方向推一步**。

   #### 4.3 修复（提交 `8545635`）与它的边界

   **一、刷新只在「cookie 送得回去的地方」发生**（两端 `src/auth.ts`）

   next-auth 的配置改成**函数形式**——只有函数形式能拿到「这次读会话的请求」，
   据此判断 cookie 送不送得回去（Server Component 分支传 `undefined`，
   Route Handler 与 middleware 传 Request）。`jwt` 回调据此决定要不要刷新
   （`makeJwtCallback(canDeliverCookie)`）。

   于是 RSC 那条路**不刷新**（只是读 cookie 里已有的令牌，不会把令牌作废），
   真正把新令牌写回浏览器的是 NextAuth 自带的 `GET /api/auth/session`——
   那条路由本来就跑 `jwt` 回调并把刷新后的 cookie 写进响应头。

   **二、多个标签页之间协调**（`src/lib/session-sync.ts` + `components/session/session-sync.tsx`）

   - 客户端组件挂在根 layout 上，页面加载时打一次**同源**的 `/api/auth/session`，
     刷新后的 cookie 由浏览器写进**共享的** cookie jar → 所有标签页一起拿到新令牌。
   - 多个标签页**同时**刷会踩（两个请求带同一枚 T0）。两道防线：
     **先占位再刷新**（抢到名额的标签页先把「有人正在刷」写进 `localStorage`
     再发请求，另一个读到占位就让路）+ **服务端的在途去重**
     （`token-refresh.ts` 的 `inFlightRefreshes` 把同一枚令牌的并发刷新合并成一次）。
   - 广播用 **`BroadcastChannel`**（瞬时通知：谁刷完了立刻告诉别人），
     `localStorage` 记**时间戳**（持久状态：后开的标签页错过了广播也能知道
     「刚刚已经刷过了」）。
     ⚠️ **两者都不传令牌**——`localStorage` 里只存**时间戳与实例 id**。
     **把长期凭证写进 JS 可读的存储，等于把 HttpOnly 降级成 XSS 可读**
     （所以「广播 refreshToken」在这个架构下是多余且有害的）。

   **对照实验**（真实浏览器 ego lite，同一段脚本、同一份「accessToken 已过期」的会话 cookie）：

   | | 标签页 A | 标签页 B | 后端 `refresh_tokens` |
   |---|---------|---------|--------------------|
   | **修复前** | 弹到 `/login` ❌ | 弹到 `/login` ❌ | **4 条 `REPLAY`** |
   | **修复后** | 留在已登录态 ✅ | 留在已登录态 ✅ | **1 条 `ROTATED`、0 条 `REPLAY`** ✅ |

   #### 4.4 ⚠️ 这是**缓解**，不是**根治** —— 两者的边界

   | | 同源多标签页 | 多浏览器 / 多设备 |
   |---|-------------|----------------|
   | **本次修复** | ✅ **已解决**（共享 cookie jar + 广播协调） | ❌ **未覆盖** |
   | **后端宽限期改造** | 不需要（但更稳） | ✅ **仍然必要** |

   - **本次修复只解决「同源多标签页」**：多个标签页共享同一个 cookie jar，
     靠「只让一个标签页去刷 + 刷完广播」就能把刷新结果共享出去。
   - **多浏览器 / 多设备之间没有共享的 cookie jar**，各自的刷新令牌互不干扰
     （所以不会互相踩），**但也共享不了刷新结果**——
     一台设备刷新了，另一台设备手里的旧令牌在宽限期外仍会被判重放。
     **这条只能靠后端的宽限期 / 幂等刷新来根治**（见 §六 遗留项 24）。

   **因此**：原「遗留项」的定性从「**必然踢下线，未解决**」改写为
   「**同源多标签页已缓解；多设备 / 多浏览器仍需后端根治**」。

   #### 4.5 修复带来的已知取舍（不是 bug，是刻意选择）

   storefront 的 RSC 页面（订单 / 地址簿 / 结算）直接带 accessToken 调后端。
   RSC 那条路现在不刷新，所以 **accessToken 刚过期后的第一次加载**，
   这些页面会先显示一次「Unauthorized」，等客户端组件刷完并 `router.refresh()`
   之后自愈。merchant-admin 没有这个现象——它的 RSC 只显示邮箱，
   所有带令牌的后端调用都在 Route Handler 里。

   这个取舍是刻意的：改之前，storefront 的 RSC **每读一次会话就轮换一次令牌**，
   而轮换结果永远送不回浏览器；改成「只在送得回去的地方刷新」之后，
   最坏情况是**闪一下错误提示**，而不再是「令牌被作废 → 下次重放 → 全族吊销」。

5. **`merchant-admin` 的 `jwt` 回调零自动化覆盖**（失败注入 #6 / #8 没抓到，见 §四）。

   - **护栏 3（L1）**：「accessToken 过期时刷新」被删掉也不会有任何测试挂。
   - **护栏 5（L1 / L18）**：「刷新失败作废会话」的**作废那一步**同样零覆盖；
     `layout.tsx` 的 `!session?.accessToken` 退回成 `!session`、
     `session` 回调的 `?? ''` 去掉，**同样一条测试都不挂**。

   根因：`auth.ts` 顶层就调 `NextAuth({...})`，import 它会初始化 next-auth 的依赖图
   （含 `server-only`），在 Vitest 里报 `Cannot find module 'next/server'`。

   **本阶段的手测（§三 场景 1 / 3）确实守住了它**，但**手测不是回归保护** ——
   下一次有人改 `auth.ts`，没有任何东西会告诉他改坏了。

   **要修**：把 `jwt` 回调里的**决策逻辑**（要不要刷新、刷新结果怎么落到 token 上）
   再往下抽一层纯函数（`refreshTokens` 与 `shouldInvalidateSession` 已经抽了，
   但「过期判断 + 分派」这一层还没抽），或者在 merchant-admin 也搭一套 jsdom 基建来测 `auth.ts`。

6. **护栏 10 的「主题变了会重写 DOM」这一侧没有自动化测试**（探针 G10）。

   把 `applyTokens` 的变更检测改成「第一次之后永远不更新」，
   `theme-watcher.test.tsx` 的 **7 条用例全绿** —— 只测了「没变时不重写」的**反向**。

   **要修**：补一条「第一次拉到主题 A、第二次拉到主题 B → 断言 `--primary` 变成了 B」的用例。

7. **护栏 9（地址簿页在 `(shop)` 路由组下）没有自动化测试**（探针 G9）。

   靠**代码审查**（`find src/app -name page.tsx` 确认路径）+ **手测**
   （`--primary` / `--radius` 与库里的 `themeTokens` 逐字一致）守着。

   **要修**：可以断言「页面路径在 `(shop)` 组下」这种结构性的东西，

8. **后端挂掉时，前台把 Node 的原始错误串 `fetch failed` 显示给了用户**（实测发现，见 §三 场景 9）。

   页面**没有白屏**（护栏 11 成立），导航栏与主题都在，
   但商品列表的位置只有一行 `fetch failed`，**没有重试按钮**。

   **这不是阶段 4 引入的**（商品列表的错误处理是阶段 2b 的代码），
   但它与阶段 3 挖出的「购物车加载失败被显示成『购物车是空的』」是**同一类问题**：
   **错误被原样或错误地呈现给用户**。

   **要修**：storefront 的商品列表 / 品类 / 搜索页都要走统一的错误处理
   （可读的中文提示 + 「重试」按钮），不要让 `fetch failed` 这种原始串漏到界面上。

9. **`JWT_EXPIRES_IN` 用命令行环境变量改不生效**（实测踩到的坑）。

   `JWT_EXPIRES_IN=45s npm run start:dev` **不生效** —— `@prisma/client` 内部的 dotenv
   会加载 `api/.env`，同名变量以 `.env` 里的为准（`2h`）。
   **要改必须改 `api/.env` 本身。**
   这条值得写下来 —— 阶段 3 的验收记录里也建议过「把 `JWT_EXPIRES_IN` 调到 45 秒」，
   照着做会白跑一轮。

### 刻意的取舍（设计如此，不是没做完）

20. **主题生效延迟最长 30 秒** —— 不是「保存即生效」。
    「切回标签页立即生效」覆盖了绝大多数感知场景（实测 < 2 秒）。
21. **主题轮询的请求量** —— 每个打开的店铺页每 30 秒一个请求；后端每次查库。
22. **`token-expiry.ts` / `token-refresh.ts` 各有两份副本** —— 两个应用无共享包。
    约定「两份测试文件是同一份」（本轮**已实测两份逐行一致**）。
23. **刷新去重只在单进程内有效，扩副本前必须换 Redis 侧的分布式锁或后端幂等刷新端点**
    （设计文档 §7 遗留项 12 / L19）。`inFlightRefreshes` 是模块级变量，
    多副本下两个进程各发一次刷新 → 同一枚 refreshToken 被提交两次。
    ⚠️ **缓解**：后端 `auth.service.ts` 的 `isConcurrentRace` 对「并发竞态」有兜底
    （只拒本请求、不牵连其它设备）；**跨进程 / 跨标签页的「先后」竞态**
    已由 `8545635` 的前端侧缓解（见遗留项 4），但**跨进程**这一层仍然只在单进程内成立。
    **在换成分布式锁或幂等刷新端点之前，不要扩 storefront / merchant-admin 的副本数。**

### 后端的活（阶段 5 的第一项）

24. **后端的刷新令牌宽限期改造 —— 遗留项 4 的「根治」那一半**（阶段 5 的第一项）

    #### 24.1 它是什么

    现在后端的刷新是**纯轮换 + 无宽限期**：
    令牌 T0 被用来刷新 → 立刻标 `ROTATED`、下发 T1；
    **T0 从此作废**。再次拿 T0 来 → 判成「真正的重放」→ `revokeTokenFamily`
    **吊销该用户全部设备的登录**。

    RFC 9700（OAuth 2.0 安全最佳实践）建议改成**宽限期（grace period）**：
    旧令牌在窗口内**仍然可用**，而且**必须返回与上一次相同的那枚新令牌**
    （而不是再签一枚新的）。另一种等价的做法是**确定性派生**：
    新令牌由旧令牌**确定性地算出来**（例如 HMAC 派生），
    这样服务端不需要存「上一枚」也能算出「同一枚」。

    #### 24.2 为什么现在不做

    - **改的是认证核心**：`auth.service.ts` 的刷新判定 + `revokeTokenFamily` 的吊销逻辑，
      动它会**影响所有用户的所有设备**，风险高、回滚成本高。
    - **前端侧已经有缓解**（遗留项 4）：同源多标签页这个「最刺眼」的场景已经解决了，
      当下没有「开两个标签页就被踢」的必然故障在逼着改后端。
    - **阶段 4 的硬约束是「后端一行不改」**（§五「本阶段没有做」第 1 条），
      后端 e2e / 单测的数字全程必须与阶段 3 一致（§一 的对账表）。

    #### 24.3 要做的话该怎么设计（阶段 5 的方向）

    | 方案 | 做法 | 优点 | 代价 |
    |------|------|------|------|
    | **A. 宽限期 + 复用新令牌**（RFC 9700 推荐） | 轮换时把 T0 标成 `ROTATED` **并记下它派生出的 T1**；宽限窗口内再拿 T0 来，**返回同一枚 T1**，不吊销族 | 语义标准；客户端无需改动 | 要给 `refresh_tokens` 加「宽限期内重放返回哪枚新令牌」的可查字段 |
    | **B. 确定性派生** | T1 = HMAC(secret, T0)，服务端**不存**也能重算出同一枚 | 无需额外的状态字段；天然幂等 | 要引入一个只有服务端知道的派生密钥；令牌格式要改 |
    | **C. 幂等刷新端点** | 刷新请求带一个客户端生成的幂等键；同键的重复请求返回同一结果 | 语义最直白 | 端点要改、前端要带上幂等键；**跨设备仍是两套令牌** |

    **建议：A 或 B**（两者都符合 RFC 9700 的方向，且不要求前端配合），
    配合一个**有上界**的宽限窗口（例如 30–60 秒）——
    窗口太短挡不住「用户切个设备」的延迟，窗口太长会削弱「轮换」的安全收益。
    无论选哪个，都要**补后端 e2e**：断言「同一枚旧令牌在宽限期内刷新两次，
    两次拿到同一枚新令牌，且 `revokeTokenFamily` **不被触发**」。

    #### 24.4 与前端缓解的关系

    - **前端缓解（已做）**：解决「**同源多标签页**」——靠共享 cookie jar + 广播协调。
    - **后端宽限期（待做）**：解决「**多浏览器 / 多设备**」——
      各设备没有共享的 cookie jar，刷新结果共享不了，**只能靠后端认得「这枚旧令牌我刚发过 T1」**。
    - 两者是**互补**的，不是重复：**即使后端做了宽限期，前端的「只在送得回去的地方刷新」
      仍然必要**——否则「服务端轮换结果送不回浏览器」这个破口还在，
      每读一次会话依然会把令牌往作废的方向推。

   前端侧已经缓解了「同源多标签页」（§六 遗留项 4），但**多浏览器 / 多设备**
   只能靠后端的**宽限期**（旧令牌在窗口内仍可用、且返回同一枚新令牌，

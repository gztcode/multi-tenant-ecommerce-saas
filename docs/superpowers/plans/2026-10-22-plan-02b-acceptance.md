## 四、发现的问题

### 问题 1（严重）：`storefront` 容器镜像无法构建 —— 缺 `public/` 目录

- **现象**：`cd infra && docker compose build storefront` 失败，报
  `failed to compute cache key: failed to calculate checksum of ref …: "/app/public": not found`。
  `storefront/Dockerfile` 第 40 行 `COPY --from=builder /app/public ./public`，但仓库里没有 `storefront/public/`。
  仓库当前唯一的 storefront 镜像构建于 2026-10-21 15:56，而 Dockerfile 是 16:11 才提交的
  （`00c4f9c chore: 四个子项目的 Docker 编排与 Nginx 子域名路由`）——**这份 Dockerfile 从未成功构建过**。
  同目录的 merchant-admin 有 `public/`（5 个 svg，已入库），storefront 没有。
- **影响**：阶段 2b 的 storefront 功能**无法以容器形式交付**。现存的 3001 容器跑的是 10-21 的旧镜像，
  `/p/:slug`、`/c/:slug`、`/search` 全部 404，任何人按 README 起容器都会拿到一个「页面能开但没有商品中心」的 storefront。
- **严重程度**：高（阻断容器化交付）。
- **本轮处理**：只补了一个只含 `.gitkeep` 的 `storefront/public/`（**未提交**，工作区因此有 1 个未跟踪项
  `?? storefront/public/`），重建镜像成功、容器起得来、浏览器实测 3001 与 3011 行为一致。
  正式修法二选一：补 `storefront/public/.gitkeep` 入库，或把 Dockerfile 那行改成可选复制。

### 问题 2（中）：开发库被前一次手测污染 —— 「重磅纯棉T恤」的规格与价格全毁

- **现象**：本轮开始时，demo 租户的 `cotton-tee` 商品状态是坏的：
  - 4 个种子 SKU（`COTTON-TEE-01~04`）被置成 `INACTIVE`，价格是 `99900/88800/99900/19900`（种子本应是 `12900/12900/12900/13900`）；
  - 多了 4 个 `price=0, stock=0, code=NULL` 的 ACTIVE SKU；
  - `product_specs` 里有两个同名「尺码」维度（一个 `deletedAt` 非空），`product_spec_values` 里「黑色/白色/M/L」各有一份活值 + 一份软删值，
    还多出一个种子里没有的「红色」；
  - 结果：`products.minPrice=0`，storefront 上这个商品四个组合**全部显示 `¥0.00` + 「暂时缺货」**。
- **影响**：前台商品详情页价格全错，且 SKU 表被垃圾数据撑大。**但这是数据问题不是代码问题**——
  本轮复现验证了规格矩阵逻辑本身是对的（见 2.16/2.17：加取值不毁老价格、空改动保存幂等）。
  污染来源是 2026-10-23 03:32 与 07:16 两次**人工在界面上保存规格矩阵**的操作

### 问题 4（低，提示）：demo 租户种子商品没有图片，前台显示「暂无图片」

- **现象**：3 个已上架商品在首页/详情页封面位置都显示「暂无图片」占位。

### 问题 5（说明，非缺陷）：描述性属性的展示顺序按 key 字典序，不按录入顺序

- **现象**：按 `材质: 纯棉` → `产地: 浙江` 的顺序录入，编辑页 textarea 显示的是

  另外 Postgres `jsonb` 本身也不保证键序。**内容零丢失**（键值全在、多行格式正确），只是顺序被规范化了。
- **严重程度**：无（记录下来以免下次被当成 bug 报）。

### 第 17 项：截断测试恒真的原因

`catalog-public.e2e-spec.ts:552` 的「超长关键词被截断而不是拒绝」全文只做了一件事：

```ts
const response = await http(app).get(`...keyword=${'a'.repeat(500)}`).expect(200);
expect(response.status).toBe(200);
```

这正是阶段 1 栽过的「只断言状态码极易恒真」。截断逻辑在不在，`expect(200)` 都成立——
不截断时 500 个 `a` 依然是一个合法的 ILIKE 模式串，照样返回 200 空列表。
对比同文件第 525 行的转义用例：它断言的是 `total`（真实数据），所以第 16 项能抓到。

**这与该用例的标题相符吗？** 部分相符——它确实证明了「不拒绝」（没返回 400/422），
所以「被截断**而不是拒绝**」里的「不拒绝」这半是真的；缺的只是「被截断」这半。

**补测建议**（未实施，本次不改测试）：造一个名字里含 64 字符以上关键词的商品，
用其**后 64 个字符**搜索并断言命中——只有真的截断了才会命中。

### 第 10 项：批量原子性没有测试守着

`batch()` 的注释写着「单事务：全部成功或全部不生效」，但没有任何用例断言这一点。
把写操作逐条挪出事务后，47 条 catalog 用例照样全绿。

原因与第 17 项同类但更根本：现有的批量用例（「批量上下架」「批量删除是软删除」
「批量操作不跨租户」）都是**单条动作**，`batch()` 内部本来就只发一条 `updateMany`，
拆成逐条写的结果与不拆完全一样——原子性与否在这些用例里不可观测。

要真正守住，需要一条**能在批量中途失败**的用例：例如 ids 里混入一个会让
后续步骤抛错的 id，断言前面的更新**也没有生效**（查库确认）。
现阶段不易构造（扩展会先滤掉跨租户 id），但缺口是真实的——注释承诺的性质目前无人验证。

| `confirm` 时的媒体大小复核无覆盖——而这才是 presigned 直传路径上**唯一真正的防线**（PUT 签名里没有长度约束） | 补 e2e：按 1KB 申报签发凭证 → 直传 6MB → confirm 必须被拒 | 去掉 `actualSize > maxSize` 判断 → 该用例失败 ✅ |
| 搜索关键词的 64 字符截断无覆盖——原用例只断言 200，而 500 个 `a` 仍是合法 ILIKE 模式串 | 重写用例：造两个**前 70 字符相同、区分度在第 64 字符之后**的商品，截断后公共前缀让两者都命中（匹配数 1→2），锚定「截断真的发生了」 | 去掉 `.slice(0, MAX_KEYWORD_LENGTH)` → 该用例失败 ✅ |

> 写第二条用例时踩了个坑，值得记：**只把关键词加长是测不出截断的**。
> 截断后的关键词仍然是商品名的前缀，而 `ILIKE '%kw%'` 是子串匹配，照样命中。
> 必须让区分度落在截断点之后，匹配数才会变。

**第三项（批量操作的事务原子性）仍未覆盖，且不打算补**：`batch()` 的注释承诺
「全部成功或全部不生效」，但要构造一个能在批量中途失败的场景并不容易——
租户扩展会先把跨租户的 id 滤掉，构造不出「前几条成功、后面某条失败」的情形。
该注释目前是**无人验证的承诺**，如实记录在此。

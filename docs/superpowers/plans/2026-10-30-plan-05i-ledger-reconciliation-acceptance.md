## 一、概览

### 1.1 这一阶段做了什么

平台报表原来从 `orders` 表读抽佣，与结算单、出款单**各读各的** —— 三处口径只要有一处漂移，
报表上的数就和商家实际拿到的钱对不上。5i 把账目的口径收成一份事实源：

| 能力 | 落点 |
|------|------|
| 账目口径的**纯函数**（符号换算、按期分组、出款分桶、可申请判定） | `api/src/modules/billing/ledger.ts` |
| 按期**批量聚合**（N 期 × 3 次查询 → 固定 6 次） | `api/src/modules/billing/ledger.service.ts` |
| 平台报表切到**抽佣流水表** | `api/src/modules/billing/report.service.ts` |
| 商家侧**对账单**（列表 + 详情，含费率与逐笔明细） | `merchant-statement.service.ts` + `merchant-admin/src/app/(dashboard)/statements/` |
| 切口径前的**只读自检脚本** | `api/scripts/check-ledger.ts`（`npm run check:ledger`） |
| 出款页与对账单**共用同一份聚合** | `payout.service.ts` 的 `availablePeriods()` 改走 `LedgerService` |

**一句话**：报表、结算单、出款单、对账单，四处数字现在出自同一批流水。

### 1.2 结论

- **浏览器手测 6 步全部实测通过**（另加 3 项额外验证）；
- **失败注入 9 条（I1–I9）逐条跑完，全部符合预期**；
- 手测**翻出 1 个真实缺陷**（货款明细的「已出款」在出款单还在途时就亮出来），
  **当场改成三态**并补齐后端、前端、e2e 三层测试；
- 全量测试：api 单测 **468**、api e2e **597**（32 套）、merchant-admin **385**（27 文件）、
  platform-admin **343**（15 文件），全绿。

## 二、关键设计决策

### 2.1 「硬切 + 自检脚本」，不做双口径并存

用户拍板：**报表直接切到流水表**，但切之前先有 `npm run check:ledger` 能查账。

- 自检脚本**只读**（`NestFactory.createApplicationContext` + 平台作用域），不修数据；
- 它查三件事：缺抽佣流水的订单、缺冲回流水的订单、缺货款流水的订单；
- **零佣金订单不算缺口** —— 有货款、无抽佣是正常的（护栏 S6）。

### 2.2 佣金取结算单的**冻结值**，不重新聚合

结算单是**已确认的凭证**，以它为准。重新聚合抽佣流水会与冻结值对不上，
且结算单被「取消确认 → 重算」之后两边立刻漂移。

### 2.3 没有结算单 → `commissionAmount` 恒为 `null`，**不是 0**

「佣金是 0」与「佣金还不知道」是两回事：

- 零额抽佣的商家**有**结算单（`netAmount = 0`）；
- 没有结算单说明**佣金压根没算过**。

填 0 会让「该期还没结算」被商家误读成「该期不用扣佣」。

### 2.4 对账单**列出所有有货款的期**，不只是能出款的期

商家看到「我这期有货款，但结算单还没确认」才不用打电话问客服。
若对账单也只列能出款的期，商家只能靠客服才知道钱卡在哪一步。

### 2.5 「在途」口径收成一处常量

`IN_FLIGHT_PAYOUT_STATUSES`（`REQUESTED` / `APPROVED` / `PROCESSING`）现在**只有一处定义**
（`ledger.ts`），`splitPayoutAmounts` 与对账单的三态映射都用它。
自己再列一遍 → 出款状态机将来加一个在途状态，两处只改一处 →
对账单的「在途金额」与明细的「出款中」对不上，商家看到两个数打架。

## 三、失败注入（I1–I9）

做法：改一处 → 跑 e2e → 确认目标用例挂 → 还原 → **校验还原**（sha256 比对）。

| # | 注入点 | 目标用例 | 挂的条数 | 结果 |
|---|--------|----------|----------|------|
| I1 | 报表的冲回不取负 | 冲回符号：流水里是负数 → 报表的 reversal 是正数 | 2 | ✅ 符合预期 |
| I2 | 报表抽佣仍读 `orders`（只切一半） | 归期按流水：订单在 8 月支付、流水归期在 11 月 → 8 月的抽佣收入是 0 | 3 | ✅ 符合预期 |
| I3 | 对账单的抽佣明细改成实时聚合 | I3：商家有多期流水时，抽佣明细只含该期结算单纳入的流水 | 2 | ✅ 符合预期 |
| I4 | 对账单的应结漏掉佣金 | S4：商家看到的三个数与出款页逐分相等 | 5 | ✅ 符合预期 |
| I5 | 聚合层的结算单查询绕过租户隔离 | S1：商家 A 访问商家 B 的期 → 拿不到 B 的任何数 | 1 | ✅ 符合预期 |
| I6 | 自检脚本把零佣金订单算成缺口 | ⚠️ 零佣金订单不算缺口 | 2 | ✅ 符合预期 |
| I7 | 待出款的计算漏掉在途金额 | I7：有在途的出款单时，待出款要扣掉在途 | 1 | ✅ 符合预期 |
| I8 | 超付时抛错而不是显示超付金额 | S7：同月内退款 → 已出款 > 应结 | 1 | ✅ 符合预期 |
| I9 | 可申请判定不看结算单状态 | 结算单未确认 → 对账单说「不可申请」并给出原因 | 1 | ✅ 符合预期 |

**I3 第一次跑「挂 0 条」** —— 查证是**测试数据没落在那个形状上**（商家只有一期流水，
实时聚合与「取结算单纳入的行」结果相同）→ 补了 2 条 e2e 用例（I3、I7 的牙齿）
→ 重跑全部符合预期。

> ⚠️ **教训（第二次踩到）**：失败注入「挂 0 条」有四种成因 ——
> ① 测试数据没落在那个形状上 ② 双层防线 ③ 断言编排问题 ④ **注入脚本写错了**。
> 本阶段用**脚本化注入 + 干跑校验锚点唯一命中**把 ④ 排除了，剩下的 ① 是真缺口。

## 四、浏览器手测

环境：商家端 `http://localhost:3002`、平台端 `http://localhost:3003`，
账号 `owner@demo.platform.test / Demo12345!`、`admin@platform.test / Admin12345!`。

手测数据（demo 商家，2026-08 与 2026-07 两期，各一笔货款 + 一笔抽佣 + 一张已确认结算单）。

| # | 手测项 | 实测 | 结论 |
|---|--------|------|------|
| 1 | 商家进「对账单」 | 列出 2026-10 / 2026-08 / 2026-07 三期；导航里「对账单」在「出款」之前 | ✅ |
| 2 | 点进某一期 | 对账单 2026-08 = 货款 ¥100.00 / 佣金 ¥5.00 / 应结 ¥95.00；出款申请页同期的三个数**逐分相同** | ✅ |
| 3 | 看抽佣明细 | 1 笔，计佣基数 ¥100.00、费率 **5%**、佣金 ¥5.00 → 加总 = 佣金净额 ¥5.00 | ✅ |
| 4 | 看货款明细 | 1 笔，标「未出款」；提交申请后翻成「出款中」 | ✅（见 §五） |
| 5 | 平台超管看报表 | 2026-08 区间：抽佣收入 ¥5.00、退款冲回 ¥0.00、净收入 ¥5.00 = 该期结算单佣金净额；且 = `orders` 旧口径的 ¥5.00（**切前切后一致**） | ✅ |
| 6 | 商家在出款页申请一期 | 申请成功，出款单 `netAmount = 9500`（= ¥95.00）、`commissionAmount = 500`（= ¥5.00），与对账单「应结」**逐分相同** | ✅ |

### 4.1 额外验证（3 项）

- **2026-10（当月、无结算单）**：列表页**照样列出**，状态列给「该周期尚未结束」，
  佣金与应结显示「—」→ 验证「列出所有有货款的期」而不是「只列能出款的期」。
- **申请后对账单的变化**：已出款 ¥0.00 / **在途 ¥95.00** / 待出款 ¥0.00，
  状态列给「该期已有出款申请在处理中」→ 在途与已出款拆得对。
- **对别家的期**：返回空壳（各数为 0、`applicableKind` 为 null）而不是 404
  —— 沿用既有设计（「查不到就 404」只用于**详情**接口），商家看不到别人的数就行。

### 4.2 手测后的清理

- 手测数据已按外键依赖顺序删干净（`payout_entries` → `payouts` → `settlement_statement_entries`
  → `settlement_statements` → `commission_entries` → `merchant_receipts` → `orders`）；
- `infra/docker-compose.yml` 的临时开关（`NODE_ENV: development`、
  `FAKE_PAYOUT_ENABLED`、缩短重试延迟）**已 `git checkout --` 还原**，api 用 production 配置重启后 healthy。

## 五、手测翻出的缺陷（已修）

### 5.1 现象

对账单详情页的「货款明细」有一列「是否已出款」，出款单**还在途**（`REQUESTED`，钱没打）
时就显示「已出款」；而同一页面顶部显示的是「已出款 ¥0.00 · 在途 ¥95.00」。

**商家看到的画面**：明细说「已出款」，汇总说「在途」—— 同一页面上两个口径用同一个词。

### 5.2 根因

`claimed` 的定义是「该货款流水是否出现在 `payout_entries` 表里」，即「是否被出款单**占用**」，
与「是否已打钱」不是一回事。设计文档的表格里写的就是这个定义 ——
**实现与设计一致，是设计本身把两个概念挤进了同一个词**。

### 5.3 修法（用户拍板：改三态）

`claimed: boolean` → `payoutStatus: 'IN_FLIGHT' | 'PAID' | null`：

| 值 | 含义 | 界面 |
|----|------|------|
| `null` | 未被任何出款单纳入 | 未出款 |
| `'IN_FLIGHT'` | 被在途出款单纳入（申请了，钱还没打） | **出款中** |
| `'PAID'` | 被已打款的出款单纳入 | 已出款 |

- 后端 `loadReceiptEntries` 按出款单状态映射；
- 前端新增 `describeReceiptPayoutStatus`，未知状态回落到「未知状态」；
- 页面表头「是否已出款」→「出款状态」。

### 5.4 顺带收口的两处

- **e2e 覆盖缺口**：原先 e2e 只断言了 `payoutStatus === null` 的那条，
  `PAID` 与 `IN_FLIGHT` 在真库路径下从未被断言过 →
  补了 ① S4 用例里「被 PAID 单覆盖的那条是 `'PAID'`」的断言
  ② 一条新的 e2e（「三态：在途的出款单 → 货款明细标『出款中』」），
  用月份 `2023-04`（**全库未被任何 e2e 用过**）。
- **在途口径重复列举**：`splitPayoutAmounts` 与对账单的三态映射各写一遍
  `REQUESTED`/`APPROVED`/`PROCESSING` → 收成 `ledger.ts` 的一个常量。

### 5.5 修完后复测

- 2026-08（出款单在途）→「**出款中**」；
- 2026-07（无出款单）→「**未出款**」；
- `PAID` 由真库 e2e 覆盖。

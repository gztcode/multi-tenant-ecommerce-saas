# 阶段 5i：账目口径收口（报表切流水表 + 商家侧对账单）设计

> 依据：阶段 5g 的 L18（报表切到流水表）、5g 的 L29（商家侧看不到自己的结算单）、
> 5f 的 L24（回填是前置）、5h-2 的 L55（`availablePeriods` 的 N+1）
>
> 前置阶段：5e（抽佣流水表）、5g（结算单）、5h-1（货款流水与出款单）、5h-2（真正打款）

---

## 一、背景与问题

### 1.1 现在的账有四个数字来源

| 消费方 | 数据源 | 归期依据 |
|--------|--------|----------|
| 平台收入报表 | `orders`（按 `paidAt` / `refundedAt` 聚合） | 订单的时间戳 |
| 结算单（平台侧） | `commission_entries`（带符号流水） | 流水行的 `occurredAt` |
| 出款单 | 货款来自 `merchant_receipts`、佣金来自结算单 | 实时聚合 |
| 商家侧 | **什么都没有** —— 商家看不到自己被抽了多少 | — |

⚠️ **报表与结算单是两套口径、两套数据源。** 抽佣收入与冲回在「有流水数据的前提下」
结果一致（冲回金额都是 `order.commissionAmount` 的负数，归期都是 `refundedAt`），
但这是**巧合性的一致**，不是结构上的一致：

- 抽佣流水的类型是**可扩展的**（`CommissionEntryType` 现在有 `COMMISSION` / `REVERSAL`，
  将来加 `ADJUSTMENT` 之类），报表的 `order.aggregate` **表达不了**新类型；
- 报表只能表达「按订单聚合」，表达不了「一笔流水一行」的审计语义；
- 将来做商家侧对账、平台对账、导出时，会再多几个口径 —— 事实源不唯一，迟早漂移。

### 1.2 回填从未在本机跑过（实测）

开发库在阶段 5h-2 验收时实测：

```
已支付订单    3 笔
抽佣流水      0 行     ← 报表有数、结算单算出 0
货款流水      0 行     ← 出款金额根本算不出来
```

执行 `npm run backfill:ledger` 后：

```
抽佣流水回填：抽佣 0 行、冲回 0 行，跳过零额 3 单
货款流水回填：货款 3 行、冲回 1 行，跳过无归期退款 1 单
```

⚠️ 两件事：

1. **货款流水之前一条都没有** —— 5h-1 建的 `merchant_receipts` 只在**新支付**时写，
   历史订单从没补过 → 历史订单的钱算不出来。
2. **抽佣流水是 0，但那是「正确的 0」** —— 那 3 笔订单的 `commissionAmount = 0`
   （商家没订阅带费率的套餐）→ 零额抽佣不写行（5e 的坑 9）。
   ⚠️ **这意味着：在本机开发库上，报表切口径前后结果完全一样** ——
   验证切口径**必须造有佣金的订单**，否则测了等于没测。

### 1.3 商家看不到账

商家端只有「出款」页（申请与进度），**没有任何一页能回答「平台抽了我多少、凭什么」**。
商家发现自己到账少了，只能打电话问客服 —— 而客服也只能人工查库。

## 二、目标与非目标

### 2.1 目标

1. **单一事实源**：平台报表、结算单、出款、商家对账单四者都从
   `commission_entries` + `merchant_receipts` 取数，符号与归期口径统一。
2. **商家可自查**：商家能看到每一期的货款、佣金（**含费率**）、应结金额，
   以及逐笔明细，且明细加总与汇总**逐分相等**。
3. **回填从「文档约定」变成「可检查项」**：一个只读的自检脚本，报告缺口并在有缺口时
   以非 0 退出码结束。
4. **顺带修掉 5h-2 的 L55**（`availablePeriods` 的 N+1）—— 商家侧对账单必然要按期聚合，
   共用同一个批量方法，避免项目里有两个 N+1。

### 2.2 非目标（明确不做）

| 不做 | 理由 |
|------|------|
| **L54：回填货款漏结佣金** | 要动结算单的佣金分摊逻辑（跨阶段、风险大），另立阶段 |
| **「已退款但无退款时间」的订单** | 5f 的 L20：冲回永远无法归期，是历史数据缺陷，不是本阶段能修的 |
| **平台向商家追回超付款**（R7） | 5h-2 的调账只做了「商家向平台补」的方向，反向没做 |
| **补记抽佣流水的结算单纳入**（R8） | 要改结算单的纳入规则（跨阶段） |
| 对接真实支付渠道 | 与本阶段无关 |
| 生产部署与监控 | 本项目目前全部在本地开发环境验证 |
| 对账单导出 | 先做页面，导出另议 |

⚠️ **部分退款与多次退款在本项目不存在** —— `payment.service.ts` 的
`refund(orderNo, reason)` **没有金额参数**（整单退款），且退款后订单状态变
`REFUNDED`、不再允许退（`refund()` 的前置检查只放行 `PAID` / `SHIPPED`）→
→ 设计里不需要为「部分退款」留分支。（若将来支持部分退款，本设计的
「应结 = 货款净额 − 佣金净额」与补差机制都要重新审视。）

## 三、口径表（本阶段最重要的一张表）

| 名字 | 定义 | 数据源 | 谁在用 |
|------|------|--------|--------|
| **抽佣毛额** | Σ `COMMISSION.amount` | `commission_entries` | 结算单 `grossAmount` |
| **抽佣冲回** | Σ `REVERSAL.amount`（**恒 ≤ 0**） | `commission_entries` | 结算单 `reversalAmount` |
| **佣金净额** | 毛额 + 冲回（**可以是负数**） | 同上 | 结算单 `netAmount` |
| **货款净额** | Σ `merchant_receipts.amount`（`SALE` 正 / `SALE_REVERSAL` 负） | `merchant_receipts` | 出款 `receiptAmount` |
| **商家应结** | 货款净额 − 佣金净额 | 跨表 | 出款 `netAmount` |

### 3.1 ⚠️ 命名陷阱

**结算单的 `netAmount` 是「佣金净额」，出款单的 `netAmount` 是「商家应结」。**
两者不是一回事，差着一个「货款」。

- 商家侧新增的接口与视图**必须用不混淆的名字**：
  `commissionAmount`（佣金净额，**与出款页同名同义**）、`receiptAmount`（货款净额）、
  `payableAmount`（商家应结）；
- ⚠️ **不要在商家侧复用 `netAmount` 这个字段名** —— 那是出款单的叫法，
  拿过来会让读代码的人以为「结算单的净额 = 商家能拿的钱」。

⚠️ **`commissionAmount` 是「带符号的佣金净额」，**不是「抽了多少钱」**：

| 值 | 含义 | 商家侧怎么显示 |
|----|------|--------------|
| `+1500` | 这一期平台抽了 15 元 | 「平台佣金 ¥15.00」 |
| `0` | 这一期没抽佣 | 「平台佣金 ¥0.00」 |
| `−500` | 这一期平台**退回**了 5 元（只有冲回没有抽佣的期）| 「平台佣金 -¥5.00」 |

⚠️ **负值是合法的**：结算单的 `netAmount = grossAmount + reversalAmount`
（毛额 ≥ 0、冲回 ≤ 0）→ 「这一期只有退款冲回、没有新抽佣」时净额为负
→ 语义是「平台这一期欠商家 5 元」→ 商家应结 = 货款 − (−5) = 货款 + 5 ✅

⚠️ ⚠️ **商家端 `lib/payout.ts` 的注释说「`receiptAmount` 与 `commissionAmount`
都是正数」—— 这条注释是不准确的**（`commissionAmount` 可以是负数）。
本阶段**不改**它（不是本阶段引入的），但商家侧对账单**必须照带符号的值显示**
→ 记为遗留（§十·R10）。

### 3.2 ⚠️ 符号转换点（只有两处）

| 地方 | 口径 | 符号 |
|------|------|------|
| 结算单 / 流水表 | `reversalAmount` 恒 ≤ 0 | `netAmount = grossAmount + reversalAmount` |
| **平台收入报表** | `reversal` **恒 ≥ 0** | `netRevenue = subscriptionRevenue + commissionRevenue − reversal` |

⚠️ 这两处符号相反是**阶段 5g 就定下的**（5g 的坑 2）。报表切口径时，
`REVERSAL` 行的 `amount` 是负数 → 报表要**取负**才能得到正的 `reversal`。
**UI 语义不变**（超管看到的「冲回 ¥300.00」仍是正数、净收入仍是减法），
只在数据层换算 → 平台超管无感。

## 四、报表切到流水表

### 4.1 改什么

`api/src/modules/billing/report.service.ts` 的 `summary()`：

```ts
// 改前：抽佣收入按订单聚合
const commissionAggregate = await this.prisma.order.aggregate({
  where: { paidAt: { gte: from, lt: to } },
  _sum: { commissionAmount: true },
});
// 改前：冲回按订单聚合（正数，要减）
const reversalAggregate = await this.prisma.order.aggregate({
  where: { status: OrderStatus.REFUNDED, refundedAt: { gte: from, lt: to } },
  _sum: { commissionAmount: true },
});

// 改后：抽佣毛额 = Σ COMMISSION 行
const commissionAggregate = await this.prisma.commissionEntry.aggregate({
  where: { type: CommissionEntryType.COMMISSION, occurredAt: { gte: from, lt: to } },
  _sum: { amount: true },
});
// 改后：冲回 = −Σ REVERSAL 行（流水是负数，报表口径是正数）
const reversalAggregate = await this.prisma.commissionEntry.aggregate({
  where: { type: CommissionEntryType.REVERSAL, occurredAt: { gte: from, lt: to } },
  _sum: { amount: true },
});
```

⚠️ `reversal` 变量取 `-（REVERSAL 行之和）`。

### 4.2 为什么这样改是安全的

| 维度 | 改前（orders） | 改后（流水表） | 一致？ |
|------|---------------|---------------|--------|
| 抽佣金额 | `order.commissionAmount` | `COMMISSION.amount`（写入时取 `order.commissionAmount`） | ✅ 逐分相等 |
| 抽佣归期 | `order.paidAt` | `COMMISSION.occurredAt`（写入时取 `order.paidAt`） | ✅ 同源 |
| 冲回金额 | `order.commissionAmount` | `REVERSAL.amount`（= `-order.commissionAmount`） | ✅ 取负后相等 |
| 冲回归期 | `order.refundedAt` | `REVERSAL.occurredAt`（写入时取 `order.refundedAt`） | ✅ 同源 |
| 零额抽佣 | 订单存在但金额 0，不影响求和 | **不写行**，不影响求和 | ✅ 一致 |

⚠️ **有流水数据时两套口径结果完全一致** —— 这条是本设计的安全前提，
必须由 S5 护栏（切前切后逐分相等的用例）来守。

### 4.3 切不动的部分与它的后果

⚠️ **切口径后，「忘了回填」的后果会从「看不出来」变成「收入显示 0」。**

- 改前：报表从 `orders` 聚合 → 历史订单一直有数；
- 改后：报表从流水表聚合 → **历史订单没回填就没有流水行 → 报表显示 0**。

这是**有意的响亮失败**（5d 确立的原则：宁可起不来，也不要静默地算错），
但前提是**回填必须先跑**。由 §六 的自检脚本 + 部署顺序兜住。

⚠️ **归期口径不变** → 订阅收入那部分（`invoices`）**不动**。

## 五、商家侧对账单

### 5.1 页面与路由

| 项 | 值 |
|----|-----|
| 路由 | `/statements` |
| 侧边栏 | 「对账单」（在「出款」之上） |
| 列表 | 该商家**所有有货款流水的期**（含不能申请出款的期） |
| 详情 | 汇总 + 抽佣明细（含费率）+ 货款明细 |

⚠️ 商家端现有的 `/settlements` 是**出款**页（命名不准），**不动它** ——
改路由会打断已有链接。新页面用 `/statements`。

⚠️ 「出款」页与「对账单」页的职责边界：

| 页面 | 职责 |
|------|------|
| 出款页 | **操作**：发起申请、撤回、看进度 |
| 对账单页 | **核对**：看构成与明细、算清「我能拿多少」 |

两者会显示同一期的数据（口径一致、逐分相等），但**不重复**：出款页只列
「能申请」的期且不展开明细，对账单页列出**所有**期并给明细。

### 5.2 一期的数据结构

```ts
interface StatementPeriodView {
  /** 周期标签 '2026-08' */
  period: string;
  /** 该期结算单 id；null = 还没生成 */
  statementId: string | null;
  /** 结算单状态：DRAFT / CONFIRMED / PAID；null = 还没生成 */
  statementStatus: SettlementStatus | null;
  /** 货款净额（实时聚合） */
  receiptAmount: number;
  /** 货款流水笔数（实时） */
  receiptCount: number;
  /** 佣金净额（取结算单，冻结值）；null = 结算单还没有 */
  commissionAmount: number | null;
  /** 抽佣流水笔数（结算单纳入的） */
  commissionEntryCount: number;
  /** 商家应结 = 货款净额 − 佣金净额；null = 佣金未知（结算单还没有） */
  payableAmount: number | null;
  /** 已出款金额（该期已 PAID 的出款单之和） */
  paidAmount: number;
  /** 在途金额（该期 REQUESTED / APPROVED / PROCESSING 的出款单之和） */
  inFlightAmount: number;
  /** 待出款金额 = 应结 − 已出款 − 在途；null = 应结未知 */
  pendingAmount: number | null;
  /**
   * 已超付金额（已出款 > 应结 时成立）：> 0 = 平台多付了，需要调账。
   *
   * ⚠️ **不是理论不可能** —— 出款单的金额是**审批那一刻的快照**，
   *    而应结是**实时值**。同月内发生退款 → 货款净额变小 → 应结变小 →
   *    已出款却不变 → **已出款 > 应结**。
   */
  overpaidAmount: number;
  /**
   * 这一期可以申请**哪种**出款；null = 现在不能申请。
   *
   * ⚠️ **不能用布尔** —— 正常单已 PAID 之后还能申请**补差单**（5h-2 的机制），
   *    一个布尔装不下「可申请正常单」与「可申请补差单」两种状态。
   */
  applicableKind: 'NORMAL' | 'SUPPLEMENT' | null;
  /** 不能申请时的原因（给商家看的中文）；null = 能申请 */
  blockedReason: string | null;
}
```

### 5.2b `applicableKind` 的判定（**必须与出款页同规则**）

⚠️ **判定的权威来源是 `apply` 的实际闸门，不是列表页的筛选条件。**
出款页 `availablePeriods()` 的筛选只有一条：

```ts
if (!normalActive && !supplementActive) {
  if (amounts.entryCount === 0 || amounts.netAmount <= 0) continue;   // 无活跃单时才按金额过滤
}
```

⚠️ **列表页不按结算单状态筛选**（结算单状态只在 `apply` / `approve` 的
`assertStatementConfirmed` 里拦）→ 设计若照列表页的筛选写，会与出款页给出
不同结论 → 护栏 S4 立刻红。

⚠️ **「可申请」= 商家现在点「申请出款」会新建成一张单**，逐条照 `apply` 的路径推：

```
前置（任一不满足 → applicableKind = null）：
  周期已结束
  ∧ 有货款流水（entryCount > 0）
  ∧ 应结金额 > 0

NORMAL 可行：
  ∧ 该期没有**活跃**的 NORMAL 单（活跃 = notIn(REJECTED, CANCELLED, FAILED)，**含 PAID**）
  ∧ 该期结算单存在且状态 = CONFIRMED

SUPPLEMENT 可行：
  ∧ 该期结算单存在且状态 ∈ {CONFIRMED, PAID}    ← 补差路径 allowPaid
  ∧ 没有活跃的 SUPPLEMENT 单
  ∧ 正常单已 PAID                                  ← 正常单还在飞时，apply 会幂等返回它
  ∧ 还有未纳入的货款（supplementAmount > 0）
```

⚠️ **三条容易写错的**：

1. **「活跃」含 `PAID`** —— 正常单已出款仍然占着 `(tenantId, periodStart, kind)` 的索引位，
   仍是活跃单 → 正常单 PAID 之后 NORMAL 路径**不可达**（`apply` 会走到补差判定）。
2. **结算单状态不在列表筛选里，但在 `apply` 的闸门里** → 对账单必须照 `apply` 写，
   否则会显示「可申请」而点下去得到 409。
   ⚠️ 正常单打款成功后，结算单被联动转成 `PAID`（5h-2）→ 此时 NORMAL 路径被
   `assertStatementConfirmed` 拒（NORMAL 不开 `allowPaid`）→ 只有补差路径可达。
3. **「没有活跃的出款单」一刀切是错的** —— 正常单 PAID 之后**恰恰应该**能申请补差单。
   这正是出款页 `appliedKind` + `supplementAvailable` 两个字段存在的原因（5h-2）
   → 对账单页**沿用同一套判定**，不发明第三种。

⚠️ **这必须与出款页是同一套判定** —— 两个页面给出不同结论
（一个说能申请、一个说不能）比任何一个错都更伤信任。
→ **两边共用 §7.1 的批量聚合结果与同一个判定方法**，
由护栏 S4 守住（两个接口对同一期给出相同的 `applicableKind`）。

⚠️ **「佣金净额 > 0」这条容易漏**：零佣金的期（商家没订阅带费率的套餐）
货款是有的，但「应结 = 货款 − 0」在业务上等于「不需要出款」（钱本来就在商家账上，
平台没抽走）→ 不该出现在可申请列表里。出款页现在就是按这个规则筛的 ✅。

### 5.2c ⚠️ 「已结算」与「已出款」是两句不同的话

结算单状态在**商家侧**的文案不能沿用平台侧的：

| 状态 | 平台侧（超管看） | **商家侧（对账单用）** |
|------|-----------------|---------------------|
| `DRAFT` | 草稿 | **待确认** |
| `CONFIRMED` | 已确认 | **已确认** |
| `PAID` | 已出款 | **已结算** |

⚠️ 结算单 `PAID` 与出款单 `PAID` 都翻译成「已出款」→ 商家看到两个「已出款」
会以为是一回事。**结算单说的是「这一期的佣金定了」，出款单说的是「钱打给你了」**
→ 商家侧用「已结算」区分开。

### 5.3 ⚠️ 哪部分冻结、哪部分实时（本设计的核心取舍）

| 数据 | 来源 | 冻结还是实时 | 理由 |
|------|------|--------------|------|
| 抽佣明细 | **结算单纳入的流水**（`settlement_statement_entries` → `commission_entries`） | **冻结** | 佣金的权威值是已确认的结算单；明细必须与它逐笔一致 |
| 佣金净额 | 结算单的 `netAmount` | **冻结** | 同上 |
| 货款明细 | `merchant_receipts`（按期） | **实时** | 货款会持续回填 |
| 货款净额 | `merchant_receipts`（按期聚合） | **实时** | 同上 |

⚠️ **为什么抽佣明细不能按期实时聚合**：若按 `occurredAt` 实时取抽佣流水，
而结算单是**某一时刻生成的快照**，两者会不一致 → 商家把明细加总，
得到的数 ≠ 页面上显示的佣金净额 → **商家当场发现对不上账**。
所以明细**必须**是结算单纳入的那些行。

⚠️ **这样做的自洽性**：即便货款实时、佣金冻结，三者仍然自洽：

```
货款明细加总 = 货款净额          （同一来源，都是实时）
抽佣明细加总 = 佣金净额          （同一来源，都是结算单纳入的行）
货款净额 − 佣金净额 = 商家应结     （定义）
```

回填发生时：货款变大、佣金不变（结算单没重算）→ 应结变大 → 由**补差单**补齐
（5h-2 的补差机制）→ 逻辑闭合。

⚠️ **但「佣金」方向有一个进不去的形状**（设计审查时补上的）：
`settlement_statement_entries.entryId` 是 **unique** → **一笔抽佣流水只能被一张
结算单纳入**。若回填把一笔**抽佣流水**补到**已结算的期**：
- 它进不了旧单（旧单已生成）；
- 新单生成时 `assertEntriesNotSettled` 会抛 409（这行流水已被别的单纳入）
  → **该期永远结不了**。

→ 本阶段**不修**（要改的是结算单的纳入规则，跨阶段），但对账单的语义要写清：
**该期的佣金一律以结算单的冻结值为准，补记的抽佣流水不进对账单**。
记为遗留（§十·R8）。

### 5.4 「已出款 / 在途 / 待出款 / 超付」怎么算

```
paidAmount    = Σ 该期 kind ∈ {NORMAL, SUPPLEMENT} 且 status = PAID 的出款单的 netAmount
inFlightAmount = Σ 该期 status ∈ {REQUESTED, APPROVED, PROCESSING} 的出款单的 netAmount
pendingAmount  = max(0, 应结 − paidAmount − inFlightAmount)     ← 不出现负数
overpaidAmount = max(0, paidAmount − 应结)
```

⚠️ `REJECTED` / `CANCELLED` / `FAILED` 的单**都不算已出款也不算在途**：

- `REJECTED` / `CANCELLED`：没打钱 ✅
- `FAILED`：打款失败，明细已释放（5h-2 的 `markFailed` 会 `deleteMany`）→
  商家可以重新申请 → 那笔钱仍属于「待出款」✅

⚠️ **在途必须单列**（设计审查时补上的）：`REQUESTED` / `APPROVED` / `PROCESSING`
的单钱**还没打出去**，但商家点进详情会看到有一张单在飞。
若把在途也算进「待出款」，商家看到「待出款 ¥50」却发现已经有一张单在处理 → 困惑。

⚠️ **超付是真实存在的业务状态，不是 bug**：

| 场景 | 应结（实时） | 已出款（快照） | 结果 |
|------|------------|--------------|------|
| 同月内退款 | 货款净额变小 → 应结变小 | 不变 | **已出款 > 应结** |
| 跨月退款 | 冲回落**退款期** → 本期货款净额不变 | 不变 | 已出款 ≤ 应结 ✅ |

⚠️ **跨月退款为什么不算超付**：`merchant_receipts` 的 `SALE_REVERSAL` 归期是
`refundedAt`（退款发生的那一期）→ 退款在 3 月 → 3 月的货款净额是负数，
1 月的货款净额**不减** → 1 月的应结不变 ✅
⚠️ 但这带来另一个后果：**3 月的应结是负数**（货款 −100 − 佣金 −15 = −115）
→ 不能申请出款 → **平台向商家追回那笔钱没有任何机制**（5h-2 的调账只做了
「商家向平台补」的方向）→ 记为遗留（§十·R7）。

⚠️ **超付时不能抛错**：抛错会让商家**看不到自己已超付的事实** →
他要问客服，客服也要解释为什么系统报错。正确做法是显示
`overpaidAmount > 0` + 文案「本期已超付，待平台调账」。
→ 护栏 S7 相应改成「**不出现负的待出款**」，而不是「负了就抛错」。

⚠️ **佣金未知时**（该期还没有结算单）：`payableAmount = null`、
`pendingAmount = null`、`paidAmount = 0`（没有结算单就不可能有出款单）、
`overpaidAmount = 0`、`applicableKind = null`。

⚠️ **零佣金商家永远不会有结算单**（结算单生成时「该期没有流水 → 不出单」，
`settlement.service.ts` 的 `empty` 分支）→ 零佣金商家的对账单上
`statementId` 恒为 null、`commissionAmount` 恒为 null →
⚠️ **`blockedReason` 要写「本期无平台佣金，无需结算」**，
否则商家会以为平台漏出了单。

明细查询必须先校验 `statementId` 属于当前租户」→ **本阶段正是那个「将来」**。
⚠️ `payout_entries` 同款（5h-1 建它时就是纯关联表）→ 若对账单要展示

**同样必须先校验 `payoutId` 归属**。

⚠️ 商家侧的查询**不得**手写 `tenantId`（靠租户作用域扩展自动附加）。

### 5.6 明细的字段

**抽佣明细**（来自结算单纳入的流水）：

| 列 | 来源 |
|----|------|
| 时间 | `commission_entries.occurredAt` |
| 订单号 | `commission_entries.orderNo` |
| 类型 | `COMMISSION` → 「抽佣」；`REVERSAL` → 「冲回」 |
| 货款基数 | `commission_entries.baseAmount` |
| 费率 | `commission_entries.rateBps`（基点，10000 = 100%） |
| 佣金金额 | `commission_entries.amount`（**带符号**：抽佣正、冲回负） |

⚠️ **费率是逐笔的** —— 费率来自下单时的套餐快照，商家中途换套餐 → 同一期里
两笔订单费率不同（5% 与 7.5%）。这是**正常业务**，页面要能显示出来，
商家问了才能解释（见 §九·R3）。

⚠️ **DRAFT（未确认）的结算单不展示明细** —— 未确认的结算单**不是凭证**，
确认时可能被重算 → 商家看到一份「随时会变的账」会困惑。
该期只显示「结算单待确认」，佣金与明细都留空。

**货款明细**（来自 `merchant_receipts`）：

| 列 | 来源 |
|----|------|
| 时间 | `occurredAt` |
| 订单号 | `orderNo` |
| 类型 | `SALE` → 「货款入账」；`SALE_REVERSAL` → 「货款冲回」 |
| 金额 | `amount`（**带符号**） |
| **出款状态** | 该 `entryId` 出现在 `payout_entries` 里时，按其出款单的状态分三态：`null` = 未被任何出款单纳入（未出款）；`IN_FLIGHT` = 被在途出款单（`REQUESTED` / `APPROVED` / `PROCESSING`）纳入（出款中）；`PAID` = 被已打款的出款单纳入（已出款） |

⚠️ **「出款状态」这一列不是可有可无的**：货款明细是**实时**的，
里面混着「已经被出款单打过的」与「还没被纳入任何出款单的」两批 →
商家看到「这 ¥100 为什么在待出款里」时会困惑。标出来就清楚了。

⚠️ **三态而不是布尔**：「被出款单占用」≠「钱已到账」——
在途的单（申请了但钱还没打）若也标「已出款」，商家就会来投诉。
三态与页面顶部的「已出款 / 在途 / 待出款」一一对应。

⚠️ 这一列要查 `payout_entries` → 而 `payout_entries` **不受租户作用域约束**
→ 必须先校验 `payoutId` 属于当前租户（§5.5）。

### 5.7 列表页的「所有期」怎么定

**该商家所有有货款流水的自然月**（按 `merchant_receipts.occurredAt` 分组），
**按期倒序**（最新在前）。

⚠️ **「同序」只指排序，不代表集合相同**（设计审查时纠正的措辞）——
出款页的期集合是「**能申请**的期」，对账单的期集合是「**所有有货款的**期」，
后者更大（设计 §5.1 已说明这个职责边界）。

⚠️ **包含**：
- 结算单未生成的期（佣金显示「待确认」，不可申请出款）；
- 结算单是 `DRAFT` 的期（同样待确认）；
- 零佣金商家的期（**永远不会有结算单** → 佣金显示「本期无平台佣金，无需结算」，
  见 §5.4 末尾）；
- 已出款完毕、货款被回填的期（应结变大，待出款 > 0 → 可申请补差）；
- 同月内退款导致**超付**的期（显示超付金额，见 §5.4）。

⚠️ **不包含**：完全没有货款流水的月（连月份都不出现）。

⚠️ **未结束的当月**：货款流水按 `occurredAt` 分组时**会包含当月**（今天还在收款）
→ 对账单要把它列出来（商家能看到「本月已经收了多少钱」），
但 `applicableKind = null`（周期未结束，不能申请出款）→
⚠️ 出款页的 `availablePeriods` 是**先查再按 `resolved.to > now` 跳过**当月的，
两个页面的期集合在这一个月上不同 —— **这是有意的**（对账单要能看当月）。

⚠️ **不分页**：期数 = 有货款的月数，最多几十行 → 分页控件是纯负担
（5h-1 的遗留里正好有「列表补分页控件」这一条，但那是给**出款单列表**的，
按单计、可能上千条；对账单是按期计，量级完全不同 → 本阶段不做）。

⚠️ **排序不随金额变**：期是时间的自然单位，不按金额排（金额会变，排序会跳）。

## 六、回填自检脚本

### 6.1 命令与判定

```bash
npm run check:ledger
```

**只读**（不写任何数据）。输出：

```
账目流水自检
──────────────────────────────
已支付订单          3 笔
  其中抽佣额为 0    3 笔   ← 零额抽佣不写行，不算缺口
抽佣流水            0 行   ⚠️ 缺口 0（3 笔订单的抽佣额都是 0）
货款流水            3 行   ✅
货款冲回流水        1 行   ✅
已退款但无退款时间  1 单   ⚠️ 冲回永远无法归期（阶段 5f 的 L20）
──────────────────────────────
结论：流水完整
```

⚠️ **缺口判定规则**（必须精确，否则会误报 —— 设计审查时抓出过一个会永远 exit 1 的坑）：

| 缺口类型 | 判定 | 为什么 |
|----------|------|--------|
| 缺抽佣流水 | 已支付订单中 `commissionAmount ≠ 0` 的，缺 `COMMISSION` 行 | 零额抽佣**不写行**（`shouldBackfillCommission` 在 `commissionAmount === 0` 时提前 return）|
| 缺冲回流水 | 已退款、`refundedAt ≠ null` **且 `commissionAmount ≠ 0`** 的订单，缺 `REVERSAL` 行 | ⚠️ **必须带 `commissionAmount ≠ 0`** —— `shouldBackfillReversal` 同样在零额时提前 return，零佣金订单**根本不会被要求有冲回行**。漏掉这条 → **所有零佣金商家都被报成缺口 → `check:ledger` 永远 exit 1** |
| 缺货款流水 | 已支付订单中 `totalAmount ≠ 0` 的，缺 `SALE` 行 | 货款额为 0 的订单也不写行 → 同样排除 |
| 无归期退款 | 已退款但 `refundedAt IS NULL` | **不是缺口**，是永远无法归期（要单独报） |

⚠️ **必须按 `orderId` 逐单判，不能按总行数比** ——
`commission_entries` 与 `merchant_receipts` 都是 `@@unique([orderId, type])`
（一单一抽佣、一单一冲回；一单一货款入账）→ 逐单查「这个 orderId 有没有对应行」。

⚠️ **「已支付订单」= `paidAt IS NOT NULL`**（与两个 `backfill()` 的口径逐字一致）——
⚠️ **不能按 `status = PAID` 统计**：`SHIPPED` 的订单也付过钱，
按 status 统计会与 backfill 的口径不一致 → 报出假缺口。

⚠️ **退出码**：有缺口 → 1；无缺口 → 0。⚠️ 「无归期退款」**不导致非 0 退出**
（它是历史数据缺陷，不是部署漏做），但要单独报出来。

### 6.2 部署顺序（写进 README 与验收记录）

```
1. 部署旧版本
2. npm run backfill:ledger     ← 回填（幂等，可重复跑）
3. npm run check:ledger        ← 必须 exit 0
4. 部署新版本（报表已切口径）
```

⚠️ 回填是**幂等**的（5e 的设计：先查后插），重复跑安全。

## 七、数据模型与共享的聚合层

### 7.1 ⚠️ 必须新增一个「按期批量聚合」方法（现有结构下无法直接共用）

⚠️ 现有的 `computeAmounts(tenantId, period)` 是 **private** 且**只算一期**
（`payout.service.ts:858`）→ 对账单要一次算**所有期**，无法直接复用。

⚠️ 而且 `availablePeriods()` 现在是**逐期循环**调用它的（每期 3 次查询：
金额 + 正常单 + 补差单，可能再加一次未纳入金额）→ 这就是 5h-2 的 L55（N+1）。

**做法**：新增一个批量方法，两边共用：

```ts
/**
 * 一次查齐所有期的货款 / 佣金 / 出款，内存里按期分组。
 *
 * ⚠️ **必须一次查完再分组** —— 逐期查询就是 N+1（5h-2 的 L55）。
 */
async function aggregatePeriods(
  tenantId: string,
  periods: Array<{ from: Date; to: Date }>,
): Promise<Map<string, PeriodAmounts>>
```

- `availablePeriods()` 改用它 → **N 次查询变 1 次**；
- 商家侧对账单用它 → 同一份聚合，两边数字**必然一致**（护栏 S4 的实现基础）。

⚠️ **`availablePeriods()` 的返回结构不变** —— 仍然是「可申请的期」的列表
（聚合后再按原有规则过滤掉）→ **`merchant-admin` 的 `AvailablePeriod` 类型与
申请页不需要改**。⚠️ 只有当实现时发现「聚合结果里有出款页用不上的信息」，
才考虑加字段 —— 那时要在设计里补一句，不在实施时临时决定。

### 7.2 不新增任何表、不改任何字段

| 需要的数据 | 已有来源 |
|-----------|---------|
| 货款 | `merchant_receipts` ✅ |
| 佣金 | `settlement_statements` + `settlement_statement_entries` + `commission_entries` ✅ |
| 出款 | `payouts` + `payout_entries` ✅ |

⚠️ 索引检查（**全部核实过**）：

| 表 | 索引 | 本阶段的用途 | 够吗 |
|----|------|--------------|------|
| `commission_entries` | `@@index([occurredAt])` | 平台报表的**跨租户**聚合（那条查询没有 `tenantId` 条件，走不了复合索引的前导列） | ✅ 够 |
| `merchant_receipts` | `@@index([tenantId, occurredAt])` | 商家侧按期聚合货款 | ✅ 够 |
| `settlement_statements` | `@@unique([tenantId, periodStart])` | 按期找结算单（unique 隐含索引） | ✅ 够 |
| `payouts` | **部分唯一索引** `payouts_tenantId_period_kind_active_uniq` ON `(tenantId, periodStart, kind)` WHERE `status NOT IN ('REJECTED','CANCELLED','FAILED')` | 按期找已出款 / 活跃的出款单 | ✅ 够 |

⚠️ **`payouts` 的那条部分唯一索引覆盖 `PAID`** —— 它的 `WHERE` 排除的是
`REJECTED` / `CANCELLED` / `FAILED`，**`PAID` 在索引范围内** → 查「该期已 PAID 的
出款单」能走这条索引的前缀 `(tenantId, periodStart)` ✅ **不需要加新索引**。

⚠️ **但查「该期所有出款单（含 FAILED / CANCELLED）」走不了那条索引**
（那三个状态被 `WHERE` 排除）→ 那种查询会落到 `payouts_status_createdAt_idx`
或全表扫。本阶段**不做**这种查询（只需要「已出款」「在途」「活跃」三组，
前两组里的 `PAID` 与 `REQUESTED/APPROVED/PROCESSING` 都在索引内 ✅
—— 被排除的三个状态恰好都不是我们要的）。

⚠️ `commission_entries` 在租户白名单里 → 平台作用域下扩展**不附加** `tenantId`
→ 跨租户聚合可行 ✅（5g 的注释已确认过这一点）。

## 八、护栏（S 系列）

| # | 护栏 | 落地方式 | 验证 |
|---|------|----------|------|
| **S1** | 商家只能看自己的对账单 | 租户作用域 + 明细查询前校验 `statementId` / `payoutId` 归属 | e2e：商家 A 访问商家 B 的期 → 404 / 空 |
| **S2** | 抽佣明细加总 = 结算单的佣金净额 | 服务层算完后自检 | e2e + 单测 |
| **S3** | 货款明细加总 = 货款净额 | 同上 | e2e + 单测 |
| **S4** | 对账单与出款页对同一期给出**相同的结论** | 两边走**同一个**按期聚合与可申请判定方法（§7.1 的批量方法） | e2e：同一期，两个接口的 `payableAmount` 与 `applicableKind` 都相等 |
| **S5** | 报表切口径后与切前逐分相等 | 有流水数据时两套口径一致（§4.2） | e2e：造有佣金的订单，切前切后比较 |
| **S6** | 自检脚本能识别缺口，且**不误报零佣金订单** | 变异测试：故意删一行流水 → 脚本报缺口并 exit 1；零佣金订单 → 不报缺口 | 脚本级测试 |
| **S7** | 不出现负的待出款 | 超付时 `pendingAmount = 0` + `overpaidAmount > 0`，**不抛错** | 单测 |

⚠️ **S4 是本阶段最重要的一条** —— 它保证商家在两个页面看到的数字永远一致，
这是 5h-2 那条「商家看到 ¥85 去申请却是 ¥90」的教训的延续。

⚠️ **S5 的测试必须造有佣金的订单** —— 开发库那 3 笔订单佣金为 0，
两套口径结果一样，测了等于没测（§1.2）。
⚠️ **不用新造套餐**：种子里有 `commissionBps: 500`（5%）的 trial 套餐 ——
e2e 里让商家订阅它就有佣金了（§11）。

⚠️ **S6 的「不误报」与「能识别」是一对** —— 只测「能识别」的话，
一个「把所有订单都报成缺口」的脚本也能通过 → 必须同时测零佣金订单不报缺口。

## 九、失败注入

| # | 注入点 | 必须挂掉的用例 | 护栏 |
|---|--------|--------------|------|
| **I1** | 报表的冲回**不取负** | 「切前切后逐分相等」 | S5 |
| **I2** | 报表的抽佣收入仍读 `orders`（只切一半） | 同上 | S5 |
| **I3** | 对账单的抽佣明细改成按期实时聚合（不取结算单纳入的行） | 「明细加总 = 佣金净额」 | S2 |
| **I4** | 对账单的佣金改成实时聚合（不用结算单的 `netAmount`） | 同上 + 「应结 = 货款 − 佣金」 | S2 |
| **I5** | 商家接口不校验 `statementId` / `payoutId` 归属 | 「商家 A 看商家 B 的期」 | S1 |
| **I6** | 自检脚本把零额抽佣**或零额冲回**算成缺口 | 「零额订单不算缺口」 | S6 |
| **I7** | 「已出款 / 在途 / 待出款」的拆分把在途漏掉（并进待出款） | 「待出款 = 应结 − 已出款 − 在途」 | S4 |
| **I8** | 超付时**抛错**而不是显示 `overpaidAmount` | 「同月退款 → 超付 → 显示超付金额且不报错」 | S7 |
| **I9** | 对账单的 `applicableKind` 照**列表页**的筛选写（不看结算单状态） | 「两个接口对同一期给出相同的 `applicableKind`」 | S4 |

## 十、风险

| # | 风险 | 缓解 |
|---|------|------|
| **R1** | 切口径后忘了回填 → 报表历史收入显示 0 | §六 的自检 + 部署顺序；这是**有意的响亮失败** |
| **R2** | 本机开发库佣金全为 0 → 测不出切口径的效果 | S5 的用例必须造有佣金的订单（**订阅 trial 套餐即可**，见 §11） |
| **R3** | 商家看到同一期两笔订单费率不同会来问 | 这是**正常业务**（套餐换过）。页面显示费率正是为了能解释；必要时在页面加一句「费率按下单时的套餐计算」 |
| **R4** | 「已退款但无退款时间」的订单冲回永远无法归期 | 两套口径都会漏 → 新文档与自检脚本都要说清；不假装能修 |
| **R5** | 商家侧按期聚合引入 N+1 | §7.1 的批量聚合方法，出款页与对账单共用，顺带修掉 L55 |
| **R6** | 对账单页的应结实时变 → 商家以为是记账错误 | 页面明确标注「货款按流水实时统计，平台佣金以已确认结算单为准」，并给出已出款/在途/待出款拆分 |
| **R7** | **跨月退款后，平台多付给商家的钱没有追回机制** | 货款冲回归退款期 → 被退款的那期应结为负 → 不能申请出款；而多付的那笔在**原期**已经打出去 → 5h-2 的调账只做了「商家向平台补」的方向，**没有「平台向商家追」的方向** → 本阶段不修，记为遗留 |
| **R8** | **补记的抽佣流水进不了任何结算单** | `settlement_statement_entries.entryId` 唯一 → 回填到已结算的期会撞 409 → 该期结不了。本阶段不修；对账单的佣金一律以结算单冻结值为准 |
| **R9** | 同月内退款造成**超付** | 不是错误状态，是业务事实 → 显示 `overpaidAmount` + 「待平台调账」文案，**不抛错**（§5.4） |
| **R10** | 商家端 `lib/payout.ts` 的注释说「佣金都是正数」，实际可以是负数 | 本阶段**不改**（非本阶段引入），但对账单按带符号显示。⚠️ 两份 `lib/payout.ts` 是独立副本，改要改两边 |

## 十一、测试策略

| 层 | 覆盖 |
|----|-------|
| **单测** | 按期批量聚合（纯函数 + Prisma mock）、符号换算、自检脚本的判定规则、超付时 `pendingAmount = 0` 且 `overpaidAmount > 0` |
| **e2e** | 商家侧列表/详情（含无结算单的期、含回填后的期、含超付的期）、越权、S2–S5、报表切前切后相等 |
| **脚本测试** | 自检脚本：造缺口 → 报缺口 + exit 1；补上 → exit 0；**零佣金订单 → 不报缺口** |
| **浏览器手测** | 商家看到对账单（金额与出款页一致、费率可见、明细可加总）；平台超管看报表（数字与切前一致） |

⚠️ **e2e 的月份隔离**：结算单 e2e 对 `2024-10` / `2024-12` 有「这一期**全库**恰好几张单 /
没有任何流水」的断言 → 本阶段的 e2e 月份必须避开它们（沿用 5h-2 的 `2025-08 ~ 2026-09`）。

⚠️ **e2e 里怎么造出「有佣金」的订单**（S5 的前提）：**不需要新造套餐** ——
种子里有 `commissionBps: 500`（5%）的 trial 套餐 → e2e 里让商家订阅它，
后续订单的 `commissionAmount` 就非 0 → 抽佣流水会写行 → 报表切前切后才有差别。
⚠️ **不做这一步，S5 会「绿了但什么都没验」** —— 这正是 §1.2 里开发库的真实状况
（3 笔订单佣金全为 0 → 两套口径结果一样）。

## 十二、实施顺序（Task 划分建议）

1. **纯函数层**：符号换算 + 按期聚合的纯计算部分（可单测，无 IO）
2. **自检脚本**（只读，无依赖）+ 脚本级测试
3. **报表切口径** + 切前切后相等的 e2e（S5）
4. **按期批量聚合方法**（§7.1）+ **商家侧服务层与端点**（列表 / 详情）
   + **顺带修 L55**（`availablePeriods` 改用它 → N 次查询变 1 次）
5. **商家侧前端页**（对账单列表 + 详情）
6. **失败注入 + 浏览器手测 + 验收记录**

⚠️ **为什么自检脚本排在切口径之前**：报表切口径是本阶段**唯一有「切了就没法悄悄
回退」风险的改动** —— 代码可以改回去，但切换那段时间的报表数字是错的（收入显示 0）。
→ **先把检查手段做好，再动刀**。这也符合 5d 确立的原则：宁可起不来，也不要静默地算错。

⚠️ **为什么批量聚合与商家侧服务层一起做**：出款页与对账单**必须用同一份聚合**
（护栏 S4 的实现基础）→ 分成两个 Task 会写出两套算法 → 数字漂移。

⚠️ **为什么 Task 5 的前端改动面很小**：商家端已有的「出款」页逻辑不动
（`applicableKind` 与出款页共用判定 → 数字一致），
对账单是**新增页面** → 只加路由、导航项与两个组件。

## 十三、本轮设计审查的发现

⚠️ **设计文档里的「与现有实现一致 / 共用 / 已经有」是最容易出错的地方** ——
本阶段的实施计划若照抄错的断言，会直接实现出一个「两页数字不一致」的版本。

本轮用**独立审查代理对照源码逐条核实**（8 条断言全查了），
把设计改了这些地方：

| # | 审查发现 | 设计怎么改 |
|---|----------|-----------|
| 1 | 出款页的列表筛选**不看结算单状态、不看佣金是否 > 0**（只在无活跃单时按 `entryCount`/`netAmount` 过滤）→ 我原设计的「七条前置条件」与它不符 | §5.2b 改成照 `apply` 的实际闸门逐条推导；结算单状态降级为「影响能否申请」而非「列表筛不显示」 |
| 2 | `computeAmounts` 是 private 且只算一期 → 「共用同一个方法」在现有结构下不成立 | §7.1 改成「新增按期批量聚合方法，两边共用」；顺带把 L55 的修复纳入 |
| 3 | **已出款 > 应结是可能的**（同月内退款 → 应结变小，已出款是审批快照不变）→ 我原写的「理论上不可能」是错的 | §5.4 加 `overpaidAmount`，S7 从「抛错」改成「不出现负的待出款」 |
| 4 | 回填的 `shouldBackfillReversal` 在 `commissionAmount === 0` 时提前 return → 零佣金订单**根本不会被要求有冲回行** → 我原设计的缺口判定会让 `check:ledger` **永远 exit 1** | §6.1 的判定表补 `commissionAmount ≠ 0` 前置；S6 加上「不误报」这一半 |
| 5 | 「已退款但无退款时间」的订单：两套口径都会漏 → 冲回永远无法归期 | §十·R4 保留；自检脚本单独报、不影响退出码 |
| 6 | `payout_entries` 与 `settlement_statement_entries` 一样**没有 tenantId、不在白名单** | §5.5 补进租户隔离表；货款明细的「已出款」标记要查它 → 同样先校验归属 |
| 7 | 补记的抽佣流水进不了任何结算单（`entryId` 唯一 → 撞 409） | §5.3 写清语义 + §十·R8 记为遗留 |
| 8 | 「费率逐笔不同」确实可能（费率是下单时的套餐快照，商家换套餐就变） | §5.6 保留；§十·R3 保留 |

⚠️ **审查代理提的一条我核实后不成立**：「`payouts` 缺 `(tenantId, periodStart)` 索引，
要加」—— 理由是部分唯一索引的 `WHERE` 不含 `PAID`。
⚠️ **实际那条 `WHERE` 是 `status NOT IN ('REJECTED','CANCELLED','FAILED')` → `PAID` 在索引范围内**
→ 查「该期已 PAID 的出款单」能走索引前缀 ✅ **不需要加索引**（§7.2 已写明）。

⚠️ **审查代理提的一条我核实后部分成立**：「部分退款、多次退款」是边界情况 ——
实际 `refund(orderNo, reason)` **没有金额参数**（整单退款），退款后状态变 `REFUNDED`
不再允许退 → **本项目不存在部分退款** → §二 的非目标里写明，
省掉一堆为它准备的分支。

⚠️ **我自己审出来的一条**（代理没提）：`applicableKind` 用布尔装不下
「可申请正常单」与「可申请补差单」两种状态 → 改成枚举。
⚠️ 以及「没有活跃的出款单」一刀切是错判据 —— 正常单 PAID 之后恰恰应该能申请补差单。

⚠️ **一条方法论**：「注入挂 0 条」与「设计断言写错」长得**一模一样**
（5h-2 已经吃过一次亏）。本轮审查的 8 条断言里，
**有 3 条是「设计写错了」而不是「实现变了」** → 写设计时凡是提到
「与现有实现一致」，都要先去代码里查一眼，不能凭印象。

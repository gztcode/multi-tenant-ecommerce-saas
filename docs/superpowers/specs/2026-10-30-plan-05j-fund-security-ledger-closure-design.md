# 阶段 5j「资金安全与账务闭环」设计

> 日期：2026-10-30
> 前置：阶段 5g（结算单）、5h-1（出款申请）、5h-2（真正打款）、5i（账目口径收口）
> 状态：待实施

---

## 一、背景与目标

### 1.1 这一阶段要解决什么

5g→5h→5i 把账务的**正向**链路做完了：商家收款 → 平台抽佣 → 结算单 → 出款单 → 打款，
以及报表、结算单、出款单、对账单四处共用同一份事实源（5i）。

但**反向**与**存量**有两处缺口：

| 项 | 问题 | 后果 |
|---|------|------|
| **L38 / L50** | 收款账户**明文存**；出款单还**每张存一份完整账号快照** | 数据库泄露 = 银行账号泄露 |
| **R8** | 某期结算单生成后，该期又进了新的抽佣流水（回填补录）→ 补记的流水**进不了那张已冻结的结算单** | 结算单佣金**少算** → 平台少收佣金 |

### 1.2 为什么现在做

- **L38**：schema 注释自己写着「接真实支付渠道前必须改成加密存储」。
  项目至今只有假网关，但出款执行链路（`PayoutExecuteInput.account.accountNo`）
  **已经按真渠道定死了**——接真渠道只是换个 provider 实现，届时没有时间再改存储层。
- **R8**：它**已经在报**了（`generate` 返回 `stale`），但只是「报了不修」，
  而 5i 刚把商家侧对账单做出来——商家看到的佣金就是这个少算的冻结值。
  再往后拖，缺笔的期只会越来越多。

### 1.3 明确不做的

| 不做 | 理由 |
|------|------|
| **跨期调账机制**（跨月退款后平台多付的钱怎么追回、R7） | 它的前提是「跨期退款在账上归属哪一期」这个**产品决策**，不是实现问题。单独一个阶段。 |
| **L54**（回填货款漏结佣金 → 改逐笔结佣） | 要动结算单/出款单/对账单/报表四层的不变量，且已 `PAID` 的历史期改不了。依赖跨期调账机制先落地。 |
| **账户版本化**（一商家多账户，出款单只存引用） | 调研提出的「方案 C」。它**不解决明文问题**（那一份照样要加密），却推翻了 L39「一商家一账户」的设计决策。本阶段只做字段加密。 |
| **户名 / 开户行加密** | 见 §3.7。 |
| **`commission_entries.tenantId` 加外键**（R5） | 独立的数据清洗任务，与本阶段无耦合。 |

## 二、L38：收款账户字段加密

### 2.1 威胁模型与「不变的东西」

**要防的**：数据库被读走（备份泄露、SQL 注入、内部人员导出）→ 拿到可用的银行账号。

**不变的**（这几条是护栏，任何实现都不能破坏）：

| 护栏 | 出处 | 含义 |
|------|------|------|
| **X14** | `payout.service.ts:89-94` | API 响应**永不**包含完整账号 |
| **打款依据** | `payout-provider.interface.ts:33-40` | worker 拿到的 `accountNo` 必须是**完整明文账号** |
| **快照语义** | `schema.prisma:1275-1276` | 审批那一刻的账号即打款目标；商家事后改账户**不影响**已审批的单 |
| **脱敏形状** | `payout-account.service.ts:136-141` | 掩码串 = 前 N 位打星 + 尾 4 位；≤8 位全打码 |

⚠️ **关键推论**：打款需要明文 → **解密点必须唯一且受限**。
本设计的结论是：**解密只发生在 worker 执行侧**（`payout-execution.service.ts`），
展示路径一律**不解密**（用预存的掩码串）。

### 2.2 密文格式与密钥

**格式**（与 `api/src/modules/auth/token.util.ts` 的 `encryptToken` **格式同款**，
但**失败语义相反 —— 这是刻意的分歧**）：

```
base64url( iv(12) || authTag(16) || ciphertext )
```

- 算法：AES-256-GCM
- `iv`：每次加密随机生成 12 字节（**同一明文两次加密的密文不同**）
- `authTag`：16 字节，GCM 认证标签
- 无版本前缀（简单优先；解密失败一律报错，不做格式协商）

⚠️ **为什么失败语义与 `decryptToken` 相反**：`decryptToken`（`token.util.ts:119-135`）
解密失败返回 `null` —— 对刷新令牌是对的（令牌本来就可能失效，静默返回让调用方走「重新登录」）。
但**账目密文解密失败是异常**（密文损坏 / 密钥配错 / 数据没迁移），
必须**响亮地失败**。若照抄 `null` 语义，出款会带着空账号去渠道 → **钱打不出去且没人知道为什么**。

**密钥**：

- 环境变量 `PAYOUT_ACCOUNT_ENCRYPTION_KEY`
- 用 HKDF-SHA256 从它派生 AES 密钥（salt = `multi-tenant-ecommerce-saas`，
  info = `payout-account-encryption-v1`）→ **不要求环境变量恰好 32 字节**
- `api/src/common/config/` 新增 **`assertPayoutEncryptionKey()`**（**独立函数**，不塞进
  现有的 `assertSecureConfig()` —— 那是 5h-2 已验收的启动校验，牵连它不划算），
  规则**逐条照抄 `JWT_SECRET`**：
  - 长度 < 32 → **任何环境**都启动失败
  - 等于 `.env.example` 里的占位符 → **只在 production** 启动失败
  - 调用点：`api/src/main.ts`（与 `assertSecureConfig()` 并列，早于应用创建）

⚠️ **要同步加进两处配置**（否则本地开发起不来）：
- `api/.env.example`：占位符 `change-me-in-production-at-least-32-chars-long`
  （与 `JWT_SECRET` 的占位符**不同值**，否则两个校验会互相误伤）
- `infra/docker-compose.yml`：给一个**固定的**本地开发值
  （与 `JWT_SECRET` 同款理由：每次 `up` 都换密钥的话，之前签发的快照就全解不开了）

⚠️ **为什么不用 `JWT_SECRET` 派生**：`JWT_SECRET` 轮换会让**已 `PAID` 出款单的快照永久解不开**。
对刷新令牌无所谓（过期即吊销），对「当时打给谁」的审计是致命的。
独立密钥的代价只是多一个必须配的环境变量——项目已有 `assertSecureConfig` 的先例。

### 2.3 工具的落点

**新建** `api/src/common/crypto/field-cipher.ts`：

```ts
export function deriveFieldKey(secret: string): Buffer;
export function encryptField(plaintext: string, key: Buffer): string;
export function decryptField(ciphertext: string, key: Buffer): string;  // 失败抛错
```

⚠️ **不抽 `auth/token.util.ts`**：那个文件的密钥派生 info 是
`refresh-token-grace-v1`，语义与生命周期都不同（令牌过期即作废，快照要永久可解）。
动它会碰 5c 已验收的鉴权链路，**风险不划算**。两处各有各的 HKDF info，互不影响。
**格式同款、失败语义相反**（见 §2.2）—— 这两点都要在注释里写明，否则实施者会照抄 `null` 语义。

⚠️ **解密失败一律抛错**（不返回 `null`、不吞异常）：密文损坏或密钥配错，
必须**响亮地失败**——静默返回空账号会让打款带着空账号去渠道。

### 2.4 schema 改动

⚠️ **`prisma migrate dev` 当前不可用**（5e-5：四个历史迁移 checksum 不一致，
要求 reset 会清库）→ **迁移 SQL 手写**，文件放在
`api/prisma/migrations/<时间戳>_encrypt_payout_accounts/migration.sql`，
并用 `prisma migrate diff` 核对与 schema 的一致性。

⚠️ **被改动的历史迁移是四个**（实施时不要漏）：
`20261021062421_drop_user_tenant_email_unique`、`20261022100000_add_catalog_tables`、
`20261025220000_add_billing_tables`、`20261028190000_add_settlement_statements`。

**`merchant_payout_accounts`**：

| 列 | 变化 |
|----|------|
| `accountNo String`（明文） | **改名**为 `accountNoCipher`，并把里面的数据换成密文 |
| `maskedAccountNo String`（新增） | 掩码串，`NOT NULL` |
| `encryptionVersion Int`（新增） | `0` = 尚未加密，`1` = 已加密。`@default(0)` |

**`payouts`**：

| 列 | 变化 |
|----|------|
| `snapshotAccountNo String?`（明文） | **改名**为 `snapshotAccountNoCipher` |
| `snapshotMaskedAccountNo String?`（新增） | 掩码串，可空（历史单没有快照） |
| `snapshotEncryptionVersion Int`（新增） | 同上，`@default(0)` |

⚠️ **为什么是「改名 + 加掩码列 + 加版本列」，而不是「保留 `accountNo` 却让它存密文」**：
项目里 `payment_methods.token`（`schema.prisma:1035-1041`）确实是「保留列名 + 注释说明将来加密」，
但那是一个**还没做的计划**。真做的时候保留列名会让「`accountNo` 里存的是密文」这件事
**只存在于注释里**——下一个读代码的人要么误解，要么靠翻注释才知道。
`...Cipher` 后缀是**自解释**的，且与行业惯例一致。这个取舍与先例不同，是**有意为之**。

⚠️ **掩码串必须单独存**：密文长度 ≠ 明文长度，而掩码要按明文长度打星
（`maskAccountNo` 的现有行为，`payout-account.service.ts:136-141`）→ 不解密就还原不出掩码。

⚠️ **掩码串会泄露长度**——但**现状 API 返回的就是掩码串**，所以这不是新增泄露面。

⚠️ **`encryptionVersion` 是权威的幂等判定依据**（见 §2.8）：
「这行加密过没有」**不能靠「能不能解密」猜**——密钥配错时「不能解密」会被误判成「没加密」，
脚本就会用错密钥把原文覆盖掉，**且不可恢复**。版本号是**写在数据里的事实**，不依赖密钥。

### 2.5 写入路径

| 位置 | 改动 |
|------|------|
| `payout-account.service.ts:104`（create） | 加密 `accountNo` → 存 `accountNoCipher`；算掩码串存 `maskedAccountNo`；`encryptionVersion = 1` |
| `payout-account.service.ts:77-87`（update） | 同上（`accountNo` 留空时不改密文、掩码与版本号） |
| `payout.service.ts:314`（apply 快照） | 从账户表读**密文**复制到 `snapshotAccountNoCipher`，掩码串复制到 `snapshotMaskedAccountNo`，`snapshotEncryptionVersion = 1` |
| `payout.service.ts:504`（approve 快照） | 同上（与状态更新同事务，语义不变） |

⚠️ **快照复制的是密文，不是「重新加密的密文」**：密文自带随机 iv，
重新加密会得到不同的密文——虽然都能解，但「快照 = 审批那一刻的那一份」
这个语义要求复制的是**同一份密文**。

⚠️ **复制版本号**：快照的版本号必须跟着账户走 → 账户已加密（版本 1）时，
快照也是版本 1。**版本号与密文必须同时复制**，否则会出现「密文是新的、版本号是 0」的错配。

### 2.6 读取路径

| 位置 | 改动 | 是否解密 |
|------|------|---------|
| `payout-account.service.ts:125`（商家端账户视图） | 直接返回存储的 `maskedAccountNo` | ❌ |
| `payout.service.ts:1220`（出款单视图的 `maskedSnapshotAccountNo`） | 直接返回存储的 `snapshotMaskedAccountNo` | ❌ |
| `payout-execution.service.ts:124`（打款） | 读 `snapshotAccountNoCipher` → **解密** → 传给渠道 | ✅ **运行时的唯一解密点** |

⚠️ **解密逻辑不能进 `toView` / `toPlatformView`**：一旦进了，API 响应就可能带出明文，
直接破掉 X14。

⚠️ **解密点其实有两个**（别只防一个）：
1. **运行时**：worker 执行打款（`payout-execution.service.ts`）；
2. **迁移时**：迁移脚本要解密旧明文来重加密（§2.8）——
   它是**离线工具**，不面对 API 响应，风险等级不同，但**依赖同一把密钥**。

⚠️ **版本号为 0 的行不许被当成明文用**：读路径遇到 `encryptionVersion = 0` 的行
→ **直接抛错**，文案点名「该行尚未加密，请先跑 `npm run migrate:payout-encryption`」。
不抛错而是用明文兜底，等于把「忘了迁移」变成「静默继续用明文」。

⚠️ **worker 拿不到密钥怎么办**：密钥从环境变量读，与 `JWT_SECRET` 同一层。
密钥缺失 → worker 启动失败（`assertSecureConfig`）→ 出款单卡在 `APPROVED`，
由 `PayoutScanScheduler` 的救援扫描兜住（5h-2 已有）。

### 2.7 不加密的字段及理由

`snapshotAccountName`（户名）、`snapshotBankName`（开户行）**保持明文**。

**理由**：账号是**唯一能直接用于资金转移**的字段；户名与开户行是**银行卡面上就印着**的公开信息，
单独看无法完成一次转账。加密它们会让快照列从 3 个变 6 个、读写路径复杂度翻倍，
收益却接近零。

⚠️ 这是一个**安全边界判断**，不是「忘了做」。**schema 注释里也要写明**
「户名 / 开户行**有意**保持明文，理由见 5j 设计 §2.7」——
否则下一个读代码的人会以为漏做了，进而「顺手补上」把设计改乱。

若将来账户快照要展示给更多角色，或监管要求「账号 + 户名 + 开户行」整体视为敏感信息，再一并加密。

### 2.8 存量迁移

**一次性脚本** `api/scripts/migrate-payout-encryption.ts` + `npm run migrate:payout-encryption`：

**幂等判定靠版本列，不靠「能不能解密」**：

1. 打印**密钥指纹**（派生密钥的 sha256 前 8 位）+ 待处理的行数；
2. **自动建备份表**：`merchant_payout_accounts_backup_<时间戳>`、
   `payouts_backup_<时间戳>`（`CREATE TABLE ... AS SELECT *`）→ 迁移出问题可从备份恢复；
3. 要求显式 `--force` 才写库（否则只做 dry-run，打印将要改什么）；
4. 处理 `WHERE encryptionVersion = 0` 的行（**版本列是权威依据**）：
   逐行加密 → **做「加密 → 解密 → 比对原文」的自检**（自检不过就 ROLLBACK）→
   写回密文 + 掩码串 + `encryptionVersion = 1`；
5. **在同一个事务里**写回 → COMMIT；
6. 打印「迁移 N 行，跳过 M 行」。

⚠️ **为什么不能靠「能不能解密」判定**（这是本设计里最容易写错的一处）：
「解不开」有两种完全不同的原因——**还没加密** 与 **密钥配错 / 数据损坏**。
若用启发式判断，密钥配错时会把所有行当成「明文」，**用错密钥加密并覆盖原文**，
而**原文被覆盖后不可恢复**（读路径再抛错也救不回来，数据已经没了）。
版本号是**写在数据里的事实**，不依赖密钥 → 密钥配错时脚本只会「发现该迁移的行还是版本 0」
→ 照常用（可能配错的）密钥加密 → ⚠️ **首次迁移仍无解**，因为库里没有可参照的密文。

⚠️ **所以首次迁移的防错靠三件事**：
① 备份表（出事可恢复）② 密钥指纹人工核对（`--force` 前必须核对）③ 文档写明「先确认密钥再跑」。

⚠️ **为什么单事务**：事务保证**不会产生「一半密文一半明文」的混合状态**。
脚本中途崩溃 → 事务回滚 → 回到全明文 → 重跑即可。

⚠️ **迁移窗口期**：迁移期间新旧代码不能同时跑（老代码读 `accountNo`，
新代码读 `accountNoCipher`）。**改名本身就是 DDL → 必须停机**，
这不需要额外的「并存期」设计：老代码读旧列名会立刻报「列不存在」，不会静默读错。

⚠️ **e2e 不受影响**：e2e 每轮清库重建，且**造账号一律走 API**
（`PUT /api/v1/merchant/payout-account`，9 处调用点）→ 加密在 service 层做，
e2e 的造数代码一行不用改。

### 2.9 失败模式

| 情形 | 表现 | 处理 |
|------|------|------|
| 密钥缺失 / 太短 / 是占位符 | api 启动失败 | `assertPayoutEncryptionKey()` 拒绝启动（§2.2） |
| 密文损坏 / 密钥配错 | worker 解密抛错 → 出款单卡住 | 响亮失败（不静默返回空账号）；由 `PayoutScanScheduler` 告警 |
| 存量数据未迁移 | 读到 `encryptionVersion = 0` 的行 | **读路径直接抛错**，文案点名「该行尚未加密，请先跑 `npm run migrate:payout-encryption`」 |
| 迁移脚本跑一半 | 部分行已加密 | 不会发生（单事务）；真发生了就重跑脚本（版本列判定幂等） |
| 迁移时密钥配错 | 用错密钥加密写回 | **备份表可恢复** + 指纹人工核对 + `--force` 显式确认（§2.8） |

⚠️ **不做「启动时全表扫描」的自检**：那要在每次 api 启动时把所有行拉出来解密一遍，
成本与耦合都不划算。**读路径抛错**已经足够——没迁移的行**只有被读到时**才会出问题，
而读到它的一定是打款或展示流程，那正是需要立刻知道的时候。

⚠️ **密钥校验独立成一个函数**（`assertPayoutEncryptionKey()`），
不塞进现有的 `assertSecureConfig()` —— 后者是 5h-2 已验收的启动校验行为，
往里加东西会牵连它；而且「账目密钥」与「令牌密钥」的失败理由、排查方式都不同。

## 三、R8：缺笔的可见性

### 3.1 「缺笔」是什么

某期结算单生成后，该期又进了新的抽佣流水（`commission_entries` 是 **append-only**，
全仓没有任何 `update`/`upsert`）→ 那张结算单（**冻结值**）没有纳入这些新流水
→ **结算单的佣金净额与当期真实流水对不上**。

⚠️ **偏差方向取决于缺失流水的类型**（`commission_entries` 有 `COMMISSION` 与 `REVERSAL` 两种）：

| 缺失的流水 | 结算单净额 | 商家应结（货款实时 − 佣金冻结） | 谁吃亏 |
|-----------|-----------|-------------------------------|--------|
| `COMMISSION`（正数抽佣） | **偏小** | **偏大**（多拿） | 平台少收佣金 |
| `REVERSAL`（负数冲回） | **偏大** | **偏小**（少拿） | **商家少拿钱** |

⚠️ 所以**不能说「缺笔 = 平台少收」** —— 两个方向都存在。
这恰恰说明**商家端也要提示**：缺 `REVERSAL` 时是**商家吃了亏**。

⚠️ 但**对外的口径要中立**：商家端只陈述「缺 N 笔流水，佣金以结算单为准」，
不替平台判断谁该补钱（那要看缺的是哪种流水、金额多少，涉及平台决策）。

### 3.2 判定口径：比笔数为什么够

现有实现是 `current.length !== existing.entryCount`（`settlement.service.ts:281`、`:369`）。

⚠️ 成立的前提是 **`commission_entries` append-only**：笔数没变 ⇒ 纳入的流水集合没变
⇒ 金额必然也没变。**若将来流水变得可变（可改金额 / 可改归期），这里必须改成比金额之和**。
这条前提已写在 `settlement.service.ts:268-275` 的注释里，本阶段沿用。

### 3.3 平台端

**后端**：

- `SettlementView` 加 `missingEntryCount: number`（0 = 不缺笔）
- `SettlementService.list()`（`:784-814`）：在现有 `Promise.all` 里**加 1 次**批量查询
  → 查询次数 **3 → 4**（不随行数增长）
- `SettlementService.detail()`：加 1 次 `entriesInPeriod` → **4 → 5**
  （现状是 4 次：`settlementStatement.findFirst` `:825` + `settlementStatementEntry.findMany` `:832`
  + `commissionEntry.findMany` `:838` + `tenant.findMany` `:891`）

⚠️ **批量查询的分组必须按流水自己的归期，不能用账单的 `periodStart` 去筛流水**：
`commission_entries` 表**只有 `occurredAt`，没有 `periodStart` 列**（`schema.prisma:650`），
所以「按 `(tenantId, periodStart)` 分组」这个说法**实现不了**。
正确做法：按 `occurredAt` 的区间取出流水 → 在内存里按
**`(tenantId, formatPeriodLabel(occurredAt))`** 分组计数 → 与账单的
`(tenantId, periodLabel)` 对应。

⚠️ **查询区间**用 `min/max` 覆盖本页所有期是**必须的**（平台端列表可跨多期，
周期筛选是可选的）—— 但**区间只是取数的粗筛**，归期口径仍然是逐条按 `occurredAt` 算。
两者不矛盾：「不能用账单的 `periodStart` 当流水的筛选条件」才是那条真正的禁令。

⚠️ **不能用 `settlement_statement_entries` 的行数代替**：那只反映「关联行指向的流水」，
发现不了「**当期新增但未被纳入**的流水」→ 恰恰是缺笔的定义。必须查 `commission_entries` 本身。

**前端**：

- 列表页加一列「缺笔」：`missingEntryCount > 0` 时显示红色「缺 N 笔」，否则「—」
- 详情页在金额区下方给一条提示 + 修账指引

### 3.4 商家端

**后端**：

- `LedgerService.aggregatePeriods` 加**第 ⑧ 步**查询：
  `commissionEntry.findMany({ where: { tenantId, occurredAt: { gte: from, lt: to } }, select: { id: true } })`
  → 查询次数 **6 → 7**（仍固定，不随期数增长）
  ⚠️ 这一步的 `from`/`to` 是**所有期的并集区间**（方法开头已经算过），
  取回全部流水后**按 `formatPeriodLabel(occurredAt)` 在内存里按期分组**——
  与第 ① 步的 `groupReceiptsByPeriod` 同款做法。
  ⚠️ **归期口径必须是流水自己的 `occurredAt`**，不能用账单的 `periodStart` 筛流水
  （见 §3.3 的同名警告）。
- `PeriodAmounts` 加 `actualCommissionEntryCount: number`（当期真实流水笔数）
- `StatementPeriodView` 加 `missingEntryCount: number`
  （= `actualCommissionEntryCount − commissionEntryCount`，下限 0）

⚠️ **「还没生成结算单」不是「缺笔」**：没有结算单时 `commissionEntryCount` 恒为 0
（`ledger.service.ts:249`：`entryCountByStatement.get(statement.id) ?? 0`，
而 `statementId` 为 null）→ 直接相减会得到「缺 N 笔」，
把「这一期还没结算」误标成「结算单缺笔」。

→ **`missingEntryCount` 只在有结算单时才计算**；没有结算单恒为 0。
（这与 5i 的口径一致：没有结算单 → `commissionAmount` 恒为 `null`，不是 0。）

**前端**：

- 列表页「结算单状态」列旁加提示；详情页在佣金行附近加一行

⚠️ **文案要中立、只陈述事实**。商家端候选文案与取舍：

| 候选 | 问题 |
|------|------|
| 「本期结算单缺 N 笔抽佣流水，佣金以结算单为准」 | ✅ 事实陈述 + 指向权威口径。**采用** |
| 「平台少扣了您 N 笔佣金」 | ❌ 对商家有利，但会引发「那能不能多给我」与「为什么金额变了」的客服对话 |
| 「佣金待补记」 | ❌ 暗示会有后续动作，而本阶段不做 |

⚠️ **这个提示不改变任何金额**：结算单的冻结值仍是佣金的唯一口径
（`ledger.service.ts:247`），提示只是让商家知道「这一期的佣金笔数与流水对不上」。

### 3.5 修账指引：可修 vs 不可修

P6 闸（`settlement.service.ts:726-746`）判「已出款」：
存在一张 `payouts.statementId = 本单` 且 `status NOT IN (REJECTED, CANCELLED, FAILED)` 的出款单。

| 情形 | 平台端指引 | 修账路径 |
|------|-----------|---------|
| **无出款单引用** | 「可修正：取消确认后重算」 | `POST /platform/settlements/:id/unconfirm` → `POST /platform/settlements/:id/recalculate` |
| **有出款单引用** | 「该期已出款，结算单不可取消确认；缺笔部分需走调账流程」 | **本阶段无解** → 属跨期调账机制（下一阶段） |

⚠️ 已有出款单时**不能**偷偷改结算单金额——那会让「出款单金额」与「结算单金额」不再相等，
破掉 5h-2 的佣金不变量。

⚠️ P6 闸的**现有文案**已经提到了调账：
「该结算单已被出款单引用，不能取消确认。若出款已执行，请走调账流程。」
→ 说明「调账流程」这个概念在 5h-2 就已存在，只是本阶段还没建。指引文案要与它一致，不要另造说法。

## 四、测试与失败注入

### 4.1 单测

| 目标 | 用例 |
|------|------|
| 密文格式 | 同一明文两次加密的密文**不同**；都能解回原文 |
| 解密失败 | 密文被篡改 → **抛错**（不返回 null、不静默） |
| 密钥派生 | 不同 info 派生出不同密钥；同一 secret 派生结果稳定 |
| 密钥校验 | 长度不足 / 占位符 → 启动校验失败 |
| 写入路径 | create/update 存的是**密文**；`accountNo` 明文**不落库** |
| 展示路径 | 返回的掩码串与加密前**完全一致**（现有掩码行为不变） |
| 打款路径 | worker 解密后传给渠道的是**完整明文账号** |
| X14 | 出款单详情 JSON 里**不含**完整账号（现有用例继续守） |
| 缺笔判定 | 缺笔时 `missingEntryCount > 0`；不缺笔时为 0 |
| 缺笔查询次数 | 平台端列表的查询次数**不随行数增长** |

### 4.2 e2e

| 场景 | 断言 |
|------|------|
| 商家设账户 | 响应里的掩码串与明文一致；DB 里存的是密文 |
| 申请出款 | 快照列存密文；平台端视图给掩码串 |
| 打款 | 假网关收到的 `accountNo` 是**完整明文**（现有 `payout-execution.e2e-spec.ts:518` 的断言**继续成立**） |
| X14 | 出款单详情响应不含完整账号（现有用例继续守） |
| 缺笔可见 | 平台端列表/详情标出「缺 N 笔」 |
| 缺笔可修 | 未出款的期 → unconfirm + recalculate → 缺笔消失 |
| 缺笔不可修 | 已出款的期 → unconfirm 被 P6 闸拦住（409），指引文案正确 |
| 商家端提示 | 商家端对账单出现缺笔提示 |

### 4.3 失败注入

| # | 注入点 | 目标断言 |
|---|--------|---------|
| F1 | 写入时不加密（存明文） | DB 里存的是密文 |
| F2 | 写入时把**明文**存进 `...Cipher` 列 | 解密抛错 / DB 检查发现不是密文 |
| F3 | 展示路径改成返回解密后的明文 | X14 断言挂（响应含完整账号） |
| F4 | 打款路径不解密 | 假网关收到的账号是密文串 |
| F5 | 缺笔判定的不等号改成 `<=`（笔数相等也算缺笔） | 不缺笔的期被误标 → 平台端缺笔用例挂 |
| F6 | 缺笔检测漏掉「当期新增未被纳入」的流水（改查 `settlement_statement_entries`） | 缺笔用例挂 |
| F7 | 缺笔检测改用账单的 `periodStart` 去筛流水（而不是逐条按 `occurredAt` 归期） | 跨月场景的缺笔判定挂 |
| F8 | 商家端不返回缺笔字段 | 商家端提示用例挂 |
| F9 | 平台端缺笔标识恒为 0 | 平台端缺笔用例挂 |
| F10 | 读路径遇到版本号为 0 的行时**按明文兜底**（不抛错） | 未迁移行的读取用例挂 |
| F11 | 迁移脚本靠「能不能解密」判幂等（不用版本列） | 密钥配错时脚本**拒绝写库**（用例挂） |

⚠️ **失败注入必须独占**：注入期间源文件被改，与全量 e2e 并发跑会互相污染
（5i 实测：并发时全量 e2e 出现 16 条误报挂）。

## 五、风险与遗留

| 风险 | 说明 | 缓解 |
|------|------|------|
| **密钥管不好 = 全盘不可解** | 密钥丢了/换了 → 所有快照永久解不开 | 独立环境变量 + `assertPayoutEncryptionKey()` 启动校验 + 文档写明「这个密钥不能随便轮换」 |
| **迁移时密钥配错 → 原文被覆盖且不可恢复** | 首次迁移没有可参照的密文，任何自动方案都判不出「密钥对不对」 | 备份表 + 密钥指纹人工核对 + `--force` 显式确认（§2.8） |
| **`prisma migrate dev` 不可用** | 5e-5：四个历史迁移 checksum 不一致 | 迁移 SQL 手写 + `prisma migrate diff` 核对 |
| **存量迁移窗口期** | 改名是 DDL → 必须停机 | 停机窗口：停 api → 跑脚本 → 起 api |
| **掩码串泄露长度** | 现状 API 已返回掩码串 | 不是新增泄露面 |
| **户名 / 开户行仍是明文** | 见 §2.7 | 明确记录为有意取舍 + schema 注释写明 |
| **已出款的缺笔修不了** | P6 闸 | 指引明说「需走调账流程」，不假装能修 |
| **缺笔检测的归期口径** | 必须逐条按 `occurredAt` 归期，不能用账单的 `periodStart` 筛流水 | F7 注入守 |

### 5.1 本阶段留给后面的

- **跨期调账机制**（跨月退款后平台多付的钱怎么追回）—— 需先定「跨期退款归属哪一期」
- **L54**（回填货款漏结佣金 → 逐笔结佣）—— 依赖上面那条
- **R5**（`commission_entries.tenantId` 加外键）
- **5e-5**（`prisma migrate dev` 工具链修复）
- **L39**（一商家多账户 / 账户版本化）

# 阶段 5h 设计：出款（把货款结算给商家）

> 阶段 5g（结算单）已完成并合并（PR #15）。
> 本阶段接手 **5b 遗留 1 / 5e 遗留 L19**：在结算单之外，把**商家的货款**结给商家。
>
> **日期**：2026-10-29
> **依据**：`docs/superpowers/plans/2026-10-28-plan-05g-acceptance.md` §六（L19 与本阶段新发现）、
> `docs/superpowers/specs/2026-10-25-plan-05b-billing-design.md` §十一·遗留 1、
> `docs/superpowers/specs/2026-10-27-plan-05e-commission-ledger-design.md` §一·1.3
>
> ⚠️ **本阶段是 5h-1（账）**。5h-2（钱，`PayoutProvider` + 假出款网关 + 回调 + 重试）
> 单独一个阶段，**不在本文档范围内**。

## 一、目标与范围

### 1.1 目标

1. **商家知道自己该拿多少钱**：平台按自然月算出「商家应收货款 − 平台抽佣 = 应结金额」，
   商家在**自己的后台**发起出款申请，平台审批。
2. **金额在审批那一刻锁定**：申请时的数字是**预估**，审批时**重算并锁定** ——
   审批之后无论流水怎么补、结算单怎么动，已批的出款单金额不变。
3. **账能对得上**：出款单的货款明细来自一张**流水表**（不是报表 SQL 现算），
   佣金部分来自**已确认的结算单** —— 两侧口径都可追溯到具体单据。

### 1.2 范围（5h-1）

| 编号 | 子项 | 涉及 |
|------|------|------|
| 5h-1-0 | 「商家应收货款」流水表 + 支付/退款的写入点 | `api/` |
| 5h-1-1 | 商家收款账户（表 + 商家端点 + 页面） | `api/` + `merchant-admin/` |
| 5h-1-2 | 出款单表 + 状态机 + 服务层（申请 / 审批 / 拒绝 / 撤回 / 查询） | `api/` |
| 5h-1-3 | 5g 的 `unconfirm` 加「已被出款单引用」的闸 | `api/` |
| 5h-1-4 | 商家端出款端点 + 页面（申请 / 列表 / 详情） | `api/` + `merchant-admin/` |
| 5h-1-5 | 平台端审批端点 + 页面（列表 / 详情） | `api/` + `platform-admin/` |
| 5h-1-6 | 对账护栏 + 失败注入 + 验收 | 全栈 |

### 1.3 明确不做

| 不做 | 原因 |
|------|------|
| **真正打钱**（`PayoutProvider`、假出款网关、回调、失败重试） | 5h-2。5b 的原话：「出款没有现成的渠道抽象」—— 渠道那一半单独一个阶段，本阶段只把**账**做对 |
| **出款后回填的调账机制** | 回填的流水 `occurredAt` 落在已出款的期，之后再不会被选中 → 差额会永久丢失（5g 的 **L27** 同源）。本阶段记为 **L32**，留给 5h-2 的设计输入 |
| **出款单的作废重开** | APPROVED 后金额不可改；要改只能作废重开，本阶段不做（**L33**） |
| **部分退款** | 本项目的退款是**全额**（`REFUNDED` 是订单终态，冲回金额 = `-order.commissionAmount`）。部分退款会让货款口径算不出来（**L34**） |
| **多个收款账户** | 一商家一账户（**L35**） |
| **商家端导出** | （**L36**） |
| **商家侧看结算单**（5g 的 L29） | 本阶段商家侧只做出款单。结算单是**平台的佣金凭证**，商家看不到仍是盲区（**L37**） |
| **催收 / 逾期提醒** | 本项目没有告警基建（5f 的 L23） |

## 二、事实基础

### 2.1 结算单已就位（5g 的成果）

`api/prisma/schema.prisma` 里已有 `SettlementStatement`（单据头）与
`SettlementStatementEntry`（明细关联）：

- `netAmount` = 抽佣净额（毛额 + 冲回，冲回是**负数**）
- 状态机 `DRAFT ⇄ CONFIRMED`，枚举里**预留 `PAID`**（5g 的 D5：`PAID` 本阶段不可达，出款阶段必然要用）
- 周期是**自然月（UTC）**左闭右开，与本阶段一致
- 结算单是**平台的应收**（抽佣口径）—— ⚠️ 与本阶段的「应结给商家」方向相反，两者严格互补

### 2.2 抽佣流水的写入点与对称性

`api/src/modules/billing/commission.service.ts` 的两个写入点
（由 `api/src/modules/payment/payment.service.ts` 在**事务内**调用）：

| 时机 | 调用点 | 归期 |
|------|--------|------|
| 支付成功 | `payment.service.ts:871` → `recordCommissionInTx(tx, order, paidAt)` | `paidAt` |
| 退款 | `payment.service.ts:1071` → `recordReversalInTx(tx, order, refundedAt)` | `refundedAt` |

⚠️ **本阶段最重要的对称性**：货款流水的写入点与抽佣流水**在同一个事务里**，
归期口径**逐字相同** → 不可能出现「有货款、无抽佣」的**时序差**。

⚠️ 唯一的口径例外是**零额抽佣**（费率 0 / 优惠到 0 的订单）：有货款流水、无抽佣流水
→ 该商家该期**没有结算单** → 出款单的 `statementId` 必须可空（见 D8）。

### 2.3 退款是全额的

`OrderStatus.REFUNDED` 是**终态**，订单级；5e 的冲回金额 = `-order.commissionAmount`。
**没有退款金额字段，也没有退款单表** —— 退款只记了 `refundedAt`（时间）。

→ 货款流水表按同款设计：`SALE_REVERSAL.amount = -order.totalAmount`（全额）。

### 2.4 商家侧鉴权路径

商家侧的既有模式（`api/src/modules/order/merchant-order.controller.ts`）：

```ts
@Controller('merchant/orders')
@UseGuards(JwtAuthGuard)
@Roles(UserRole.MERCHANT_OWNER)
```

⚠️ **只有 `MERCHANT_OWNER` 能申请出款** —— 员工（`MERCHANT_STAFF`）不行。
出款是**打钱**，不是店铺日常操作。

⚠️ 商家侧走**租户作用域**（`tenantContext` + 租户 ID），与平台侧的
`@Roles(UserRole.PLATFORM_ADMIN)` 完全不同 —— 5g 的「商家侧工作量约翻倍」说的就是这个。

### 2.5 5b / 5e / 5g 的原始设想

| 出处 | 原文 |
|------|------|
| 5b §十一·遗留 1 | 「**抽佣出款不做** —— 只记账。将来做结算单时，从订单聚合出「本期抽佣 / 冲回 / 净额」。」 |
| 5b §九·决策 2 | 「抽佣只记账，**抽佣自动出款**」被否决 —— 理由是「**出款没有现成的渠道抽象**」 |
| 5e §一·1.3 | 「**抽佣出款**没有做」（L19） |
| 5g §一·1.3 | 「**抽佣出款**（打钱给商家）… 本阶段只记账」 |

⚠️ **这些原文的措辞把两件事混在了一起**：结算单记的是**平台从商家抽的佣**（平台的应收），
而出款是把**商家的货款**结给商家（反向资金流）。本阶段把两者的关系定清楚：

```
商家应收货款（正向）  −  平台抽佣（负向）  =  应结给商家（正向）
```

## 三、设计决策

| # | 决策 | 理由 |
|---|------|------|
| **D1** | **5h 拆成两个阶段**：5h-1（账）/ 5h-2（钱） | 账与钱是两类风险（金额算错 vs 渠道重复打钱），混在一起验收出事难定位。5h-1 不依赖渠道，可独立验收 |
| **D2** | 新建「**商家应收货款流水表**」，不改成时聚合 | 5e 的决策 D1 同样的理由：从订单现算，口径会漂 —— 上期出款后下期发生退款时，上期已出款的金额无法回溯修正 |
| **D3** | 货款流水的写入点与抽佣流水**在同一个事务** | 保证「有货款 ⟺ 有抽佣」的时序一致性（D2 的前提） |
| **D4** | **应结金额 = 货款流水净额 − 结算单佣金净额** | 与结算单严格互补，一笔账能验。佣金为负（退款多、平台佣金被冲回）时等于平台补钱给商家 |
| **D5** | 出款单**按自然月**，与结算单一对一 | 周期口径一致 → 对账清楚；`periodStart` 对齐，两边覆盖的是同一批订单 |
| **D6** | **商家申请 + 平台审批**；只有 `MERCHANT_OWNER` 能申请 | 出款是打钱，责任在店主；平台审批是第二道闸 |
| **D7** | **申请即固定流水范围，审批只锁金额** | 审批期间又来一笔流水时，出款范围不悄悄变化；审批页显示「申请时 ¥77.00 / 当前 ¥80.00」的差异 |
| **D8** | 出款单的 `statementId` **可空** | 零额抽佣的商家该期没有结算单（§2.2 的口径例外） |
| **D9** | 活跃出款单的幂等用**部分唯一索引** `WHERE status NOT IN ('REJECTED','CANCELLED')` | 拒绝/撤回后商家能**重新申请**同一周期。全量唯一索引做不到这一点 |
| **D10** | **金额全部由后端算**，请求体不接受任何金额字段 | 5g 的 D8 同款。前端再算一遍就成了第二套口径，账迟早对不上 |
| **D11** | 收款账户：**一张表、一商家一个账户、明文存 + 脱敏展示** | 本项目没有通用字段加密设施（只在 auth 模块有 JWT 相关）。schema 注释写明「接真实渠道前必须加密」，与 5b 对 `payment_methods` 的同一处理 |
| **D12** | 出款单记录**申请人**与**审批人** | 打钱是责任动作。5g 的结算单没记确认人，因为它不是责任动作 |
| **D13** | **已被出款单引用的结算单不能取消确认** | 5g 的「取消确认」是修漏结用的，但改了佣金会让已锁定的出款金额失真 |
| **D14** | 5g 的 `unconfirm` 加这道闸（D13 的落地） | 同上。⚠️ 这是本阶段**唯一**改 5g 既有行为的地方 |

## 四、数据模型

### 4.1 四张新表

#### `merchant_receipts` —— 商家应收货款流水

与 `commission_entries`（5e）**完全同款**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String @id | uuid |
| `tenantId` | String | 商家 |
| `orderId` | String | 订单（外键 Restrict） |
| `orderNo` | String | **订单号快照**（商家核对时要看） |
| `type` | `ReceiptType` | `SALE`（正）/ `SALE_REVERSAL`（负） |
| `amount` | Int | **带符号整数分**：`SALE` = `order.totalAmount`，`SALE_REVERSAL` = `-order.totalAmount` |
| `occurredAt` | DateTime | 归期：支付取 `paidAt`、退款取 `refundedAt` |
| `createdAt` / `updatedAt` | DateTime | |

约束：`@@unique([orderId, type])`（一单一货款、一单一冲回）、`@@index([tenantId, occurredAt])`。

#### `merchant_payout_accounts` —— 商家收款账户

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String @id | uuid |
| `tenantId` | String @unique | **一商家一账户** |
| `accountName` | String | 开户人姓名 |
| `bankName` | String | 开户行 |
| `accountNo` | String | 银行账号 ⚠️ **明文存**（D11），界面只展示脱敏（尾号 4 位） |
| `createdAt` / `updatedAt` | DateTime | |

⚠️ 属于**租户作用域模型** → 登记进 `TENANT_SCOPED_MODELS`。

#### `payouts` —— 出款单

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String @id | uuid |
| `tenantId` | String | 商家 |
| `payoutNo` | String @unique | 出款单号（对外凭证，服务端生成；**生成规则与撞号重试照抄 5g 的 `generateStatementNo`**） |
| `periodStart` / `periodEnd` | DateTime | 自然月区间（与结算单同口径） |
| `statementId` | String? | 引用的结算单，**可空**（D8）—— **建外键** `Restrict`（结算单不可删，与 5g 的 `settlement_statement_entries.statementId` 同款） |
| `receiptAmount` | Int | 货款净额（正数） |
| `commissionAmount` | Int | 佣金净额（**正数** = 抽了多少，与结算单 `netAmount` 同号） |
| `netAmount` | Int | **应结金额** = `receiptAmount − commissionAmount` |
| `entryCount` | Int | 纳入的货款流水笔数 |
| `status` | `PayoutStatus` | `REQUESTED` / `APPROVED` / `REJECTED` / `CANCELLED`（`PAID` / `FAILED` 预留，5h-2 用） |
| `requestedBy` | String | 申请人的用户 ID（D12） |
| `approvedBy` | String? | 审批人的用户 ID（D12） |
| `rejectedReason` | String? | 拒绝原因 |
| `requestedAmount` | Int | **申请时的预估金额**（与 `netAmount` 可能不同，用于展示差异，D7） |
| `requestedAt` / `approvedAt` / `cancelledAt` | DateTime? | |
| `createdAt` / `updatedAt` | DateTime | |

⚠️ **`statementId` 建外键，但外键管不了租户**：外键只保证「引用的结算单存在」，
**不保证它是本租户的** → 跨租户挂载仍要靠 **service 层显式校验**（同 5g 的 P9 教训）。

⚠️ `payouts` 另有 `@@index([status])` —— 平台侧的「待审批列表」按状态查。

#### `payout_entries` —— 出款单明细关联

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String @id | uuid |
| `payoutId` | String | 出款单（外键 Cascade） |
| `entryId` | String @unique | 指向 `merchant_receipts.id`（外键 Restrict）—— **一笔货款只能被出款一次** |
| `createdAt` | DateTime | |

⚠️ **不带 `tenantId`** → **刻意不登记**进 `TENANT_SCOPED_MODELS`，
与 5g 的 `settlement_statement_entries` 同款：service 层必须自己校验归属。

⚠️ **部分唯一索引**：Prisma 的 `@@unique` 表达不了「按状态条件唯一」，
所以活跃单的唯一性写在**迁移 SQL** 里（与 `payments` 表的三个部分唯一索引同款做法）：

```sql
CREATE UNIQUE INDEX "payouts_tenantId_active_period_uniq"
ON "payouts" ("tenantId", "periodStart")
WHERE "status" NOT IN ('REJECTED', 'CANCELLED');
```

⚠️ **schema 里不要声明它** —— 声明了也不生效（Prisma 表达不了部分唯一索引），
只会让人误以为约束已经在数据库层。这条注释要照抄 `payments` 表的写法。

### 4.2 枚举

```prisma
enum ReceiptType {
  /** 货款入账（正数） */
  SALE
  /** 货款冲回（负数）：全额退款 */
  SALE_REVERSAL
}

enum PayoutStatus {
  /** 待审批（商家已申请） */
  REQUESTED
  /** 已审批，金额已锁定 */
  APPROVED
  /** 已拒绝（商家可重新申请） */
  REJECTED
  /** 已撤回（商家主动撤销，仅 REQUESTED 可撤） */
  CANCELLED
  /** 已出款（5h-1 不可达，5h-2 用） */
  PAID
  /** 出款失败（5h-1 不可达，5h-2 用） */
  FAILED
}
```

## 五、金额计算与锁定

### 5.1 计算式

```
receiptAmount    = Σ merchant_receipts.amount            （该商家该自然月）
commissionAmount = 结算单?.netAmount ?? 0                （该商家该自然月、已 CONFIRMED）
netAmount        = receiptAmount − commissionAmount      ← 应结给商家
```

⚠️ **符号约定**（这一类已坑过两次，见 §七）：
结算单的 `reversalAmount` 是**负数**、平台收入报表的 `reversal` 是**正数**。
本阶段的出款单统一站在**商家应收**角度：`commissionAmount` 用**正数**表示
「抽了多少」（与结算单 `netAmount` 同号），`netAmount = receiptAmount − commissionAmount`。

### 5.2 锁定的时机

| 时点 | 金额语义 | 是否锁定 |
|------|---------|---------|
| 商家申请时 | **预估** → 写入 `requestedAmount` | 否 |
| 平台审批时 | **重算** → 写入 `netAmount` / `receiptAmount` / `commissionAmount` | ✅ **锁定** |
| 5h-2 打款时 | 读锁定值 | ✅ |

⚠️ 审批页要展示差异：「商家申请时看到 ¥77.00 / 当前 ¥80.00」。

⚠️ **差异只展示、不阻断**：金额变了**不**要求审批人填原因、也**不**设阈值 ——
由审批人看情况决定通过与否。多一个「差异原因」字段就多一处要填的空、
多一个没人填的必填项。

### 5.3 边界

| 情形 | 处理 |
|------|------|
| 应结金额 ≤ 0 | 拒绝申请（400「该期无应结金额」）—— 货款 0 的期没什么可出 |
| 该期结算单未 `CONFIRMED` | 拒绝申请（409） |
| 该期结算单不存在（零额抽佣） | `statementId` 为 null，佣金按 0（D8） |
| 该期没有货款流水 | 拒绝申请（400） |
| 收款账户未填 | 拒绝申请（400） |

## 六、数据流

### 6.1 货款流水的写入

| 时机 | 抽佣流水（5e 既有） | 货款流水（本阶段新增） | 归期 |
|------|--------------------|---------------------|------|
| 支付成功 | `recordCommissionInTx(tx, order, paidAt)` | `recordReceiptInTx(tx, order, paidAt)` | `paidAt` |
| 退款 | `recordReversalInTx(tx, order, refundedAt)` | `recordReceiptReversalInTx(tx, order, refundedAt)` | `refundedAt` |

两者在 `payment.service.ts` 的**同一个事务**里写入。

⚠️ **跳过的条件照抄抽佣**：`commission.service.ts` 里有「零额（免费套餐）」与
「没付过钱」两种跳过，货款流水要按同款处理（`order.totalAmount === 0` 的订单不写货款流水）。

### 6.2 申请 → 审批链路

```
商家（MERCHANT_OWNER）申请，选周期
  ├ ⚠️ **幂等检查放最前**：该期已有活跃出款单 → **原样返回它**
  │    （不报错、不重算金额 —— 金额已锁定。同 5g 的 D10）
  ├ 校验：周期已结束 / 该期结算单已 CONFIRMED（若存在）/ 有货款流水
  │        / 收款账户已填 / 应结金额 > 0
  ├ 创建出款单 REQUESTED
  │   · 记申请人、申请时间、预估金额（requestedAmount）
  │   · **固定纳入的货款流水** → 写 payout_entries
  └ 商家可撤回 → CANCELLED
        （本租户的任一 MERCHANT_OWNER 都能撤，不限申请人）

平台（PLATFORM_ADMIN）审批
  ├ 重算当前应结金额 → 与 requestedAmount 对比（差异展示）
  ├ 通过 → APPROVED（锁定金额、记审批人、记审批时间）
  └ 拒绝 → REJECTED（必须记原因）
```

⚠️ **审批不重新纳入流水**（D7）—— 范围在申请时就固定了。

### 6.3 商家端的「可申请周期」查询

一次返回该商家每个可申请周期的：货款净额 / 佣金 / 应结金额 / 结算单状态。
商家据此选周期，**不自己算金额**（D10）。

## 七、护栏与错误码

### 7.1 护栏清单

| # | 护栏 | 落地方式 |
|---|------|---------|
| **P1** | 同一商家同一周期只能有一张**活跃**出款单 | 部分唯一索引（D9）+ 申请**幂等**（重复申请返回既有单，不报错，同 5g 的 D10） |
| **P2** | 一笔货款流水只能被出款一次 | `payout_entries.entryId` 唯一（同 5g 的 D9） |
| **P3** | 引用的结算单必须已 `CONFIRMED` | 申请时校验，未确认 → 409 |
| **P4** | 金额全部由后端算 | DTO 里没有任何金额属性（D10） |
| **P5** | 审批时**重算**金额 | 审批服务重新聚合（D7） |
| **P6** | **已被出款单引用的结算单不能取消确认** | 改 5g 的 `unconfirm`（D13/D14） |
| **P7** | 状态机严格 + **条件更新** | 非法转换 409；`updateMany` where 带 `status` —— 申请/审批/撤回并发互斥 |
| **P8** | `APPROVED` 后金额不可变 | 只改状态不改金额字段 |
| **P9** | 商家只能操作自己的数据 | 商家侧走租户作用域；`payout_entries` 不在白名单 → **service 层必须显式校验 tenantId** |
| **P10** | 角色边界 | 申请/撤回 = `MERCHANT_OWNER`；审批 = `PLATFORM_ADMIN`；越权 403 |

### 7.2 错误码

| 码 | 场景 |
|----|------|
| 400 | 周期格式非法、该期无应结金额（≤ 0）、没有货款流水、收款账户未填 |
| 401 / 403 | 未登录 / 角色不对 / 越权访问他人出款单 |
| 404 | 出款单不存在 |
| 409 | 状态机非法、结算单未确认（或已被取消确认）、结算单已被出款单引用不能取消确认 |

⚠️ **「该期已有活跃出款单」不是 409** —— 它是**幂等**（返回既有单），
与 5g 的 D10 同款。申请方是商家自己，重复提交是网络重试或手滑，
报错会让商家以为申请失败。

### 7.3 并发场景

| 场景 | 预期 |
|------|------|
| 两个商家同时申请同一周期 | 各自成功（不同 tenantId） |
| **同一商家并发申请同一周期** | 一个成功，另一个**幂等返回同一张**（不是 409） |
| 两个超管并发审批 | 一个成功，另一个 409「已被审批」 |
| 商家撤回与平台审批并发 | 条件更新互斥 → 一个成功，另一个 409 |
| 两个商家申请同一周期但各自有货款 | 各自一张单，互不影响 |

### 8.2 失败注入（逐条单独跑，不叠加）

| # | 注入 | 期望挂掉 |
|---|------|---------|
| F1 | 申请时去掉「周期已结束」校验 | 周期校验 |
| F2 | DTO 接受金额字段（后端采信前端金额） | P4 |
| F3 | 审批时不重算（直接用申请时的金额） | P5 |
| F4 | 去掉「结算单已 CONFIRMED」校验 | P3 |
| F5 | 5g 的 `unconfirm` 去掉「已被出款单引用」的闸 | P6 |
| F6 | 申请去掉「先查后插」的幂等分支 | P1 |
| F7 | 审批/撤回的条件更新去掉 `status` | P7 |
| F8 | 商家端点去掉 `@Roles(MERCHANT_OWNER)`（员工也能申请） | P10 |
| F9 | 商家端点不校验 `tenantId`（能操作别家的出款单） | P9 |
| F10 | 审批之后仍能改金额（去掉「APPROVED 后不可改」） | P8 |

⚠️ **P2（`entryId` 唯一）不用注入**：它是**数据库层约束**，
用 e2e 直接插第二条关联行、断言 DB 抛 P2002 即可（5g 的 S4「数据层兜底」同款做法）——
注入「去掉唯一索引」反而测不出真实行为。

⚠️ **5g 的教训直接适用**：注入「挂 0 条」时先问「**测试数据有没有落在那个形状上**」，
别急着下「护栏不存在」的结论。

### 8.3 浏览器手测清单

用**假网关走真实支付**产生货款流水（同时验证写入点）：

1. 商家登录 merchant-admin → 设置收款账户（脱敏展示）
2. 商家申请出款（选周期）→ 看到预估金额 → 提交 → 状态「待审批」
3. 平台登录 → 待审批列表 → 详情 → **通过** → 状态「已审批」，金额锁定
4. 商家侧看到「已审批」；再点「撤回」→ 409（已审批不可撤）
5. 另一张单：商家撤回 → 「已撤回」；平台对已撤回的单审批 → 409
6. 另一张单：平台拒绝 → 「已拒绝」→ 商家**重新申请同一周期** → **成功**（幂等位已释放）
7. 商家 A 访问商家 B 的出款单 → 403/404
8. 员工账号（`MERCHANT_STAFF`）申请出款 → 403

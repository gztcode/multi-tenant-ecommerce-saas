## 一、目标与非目标

### 目标

后端刷新令牌支持 **RFC 9700 风格的宽限期（grace period）**：一枚刚被轮换的刷新令牌，
在**有上界的窗口内**再次被提交时，**返回与第一次完全相同的那枚新令牌**，
既不吊销令牌族，也不把它判成「真正的重放」。

配套把阶段 4 遗留的两项**测试与文档债**清掉：

1. `merchant-admin` / `storefront` 的 `auth.ts` 决策逻辑**零自动化覆盖**
   （阶段 4 验收记录 §六·5）——抽成纯模块并补单元测试。
2. README 里「跑 e2e 前必须先停掉 api 容器」的警告**已经过时**
   （队列前缀隔离与每轮清库早已实现）——核实并更正。

### 非目标（本阶段明确不做）

| 不做的事 | 为什么 |
|---|---|
| **多设备 / 多浏览器共享会话** | 宽限期不改变「各设备各自登录、各持独立令牌」这个事实。它只是让「同一枚令牌被短时间重复提交」不再牵连全族 |
| **令牌泄漏后的长期防护** | 60 秒后泄漏的令牌仍然会导致全族吊销。宽限期把「永久」缩到 60 秒，不是消除 |
| **跨副本的分布式刷新锁** | 前端 `inFlightRefreshes` 是模块级变量，只在单进程内有效。宽限期让跨副本的**后果**变轻（拿到同一枚令牌而不是被踢），但没有消除重复请求 |
| **前端「只在 cookie 送得回去的地方刷新」的改动** | 阶段 4 提交 `8545635` 已解决（`src/auth.ts` 改成 next-auth 的函数形式）。它与宽限期**互补**，都必要：否则「服务端轮换结果送不回浏览器」这个破口还在，每读一次会话就把令牌往作废方向推一步 |
| **阶段 4 的其余前端技术债** | 主题 token / 分组标量 / 商家后台实时预览 / 前台错误处理 / merchant-admin 的 jsdom 基建 —— 属于**阶段 5d** |
| **计费遗留项** | 抽佣流水明细、M11 可观测性、换套餐的周期长度语义 —— 属于**阶段 5d** |
| **`maxStores` 的约束点** | 依赖尚不存在的「新增店铺」接口，本阶段无从下手 |

## 二、关键决策速查

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | 宽限期实现 | **宽限记录里存新令牌的密文** | 服务端只存 hash，要「返回同一枚新令牌」就必须能重算出明文。存**明文**会与 `token.util.ts` 里既有的「不存明文」原则正面冲突，且**备份与流复制里的明文抹不掉**（见 §5.1） |
| D2 | 窗口长度 | **60 秒，固定，不因重放延长** | 覆盖客户端超时（10–30s）+ 重试退避；对「令牌泄漏」的封窗仍然很短 |
| D3 | 并发与「先后」的切分 | **不切分，宽限期内一律返回同一枚** | 实测证明切分依赖时序（见 §五·3），会把现有并发测试变成 flaky |
| D4 | 时钟源 | **应用时钟**（清理任务除外，见 §4.6） | 与同文件里现有的 `revokedAt` / `expiresAt` 保持一致。同一段逻辑里混用两个时钟源会造成更隐蔽的错（写 A 读 B） |
| D5 | 宽限期内返回什么 | **refreshToken 同一枚，accessToken 重新签发** | accessToken 是无状态 JWT，重签无害且顺延会话；refreshToken 必须同一枚才谈得上「幂等」 |
| D6 | 密文的清理 | **BullMQ 重复任务，每小时一次** | 惰性清理不够：客户端轮换后就不再用旧令牌，绝大多数行永远等不到人来抹。清理后表更小、密钥轮换的影响面也更小 |
| D7 | 前端配套 | **含**（抽纯模块 + 补单测 + 更新过期注释） | 宽限期改变了后端语义，前端注释不改就是骗人 |
| D8 | 加密密钥的来源 | **HKDF 从 `JWT_SECRET` 派生** | 不新增必须配置的环境变量（避免 breaking），且密钥职责分离（派生而非直接复用）。见 §4.2 |
| D9 | 宽限期内放行前是否检查目标令牌 | **要检查**（实施期补上，见 §5.6） | 不检查的话，**登出后重放前身令牌能换回一枚有效的 accessToken** —— 登出的意图被撤销。`ROTATED` 的目标要放行（链式自愈依赖它），`LOGOUT` / `REPLAY` 的拒绝且**不吊销全族** |

## 三、现状：现在为什么会「开两个标签页就被踢下线」

### 3.1 当前的刷新流程

`api/src/modules/auth/auth.service.ts` 的 `refresh()`：

```
令牌不存在                       → 401
令牌已吊销（revokedAt 非空）      → 分三档：
    ① 轮换时间 ≥ 本次请求起始     → 并发竞态 → 401，只拒本请求，不牵连其它设备
    ② 吊销原因是 LOGOUT           → 401，不牵连其它设备
    ③ 其它（真正的重放）           → revokeTokenFamily 吊销该 userId 下全部令牌 → 401
令牌未吊销：
    expiresAt 已过                 → 401
    否则 → 条件更新轮换（where 带 revokedAt: null）→ count === 0 说明被别人抢先 → 重读再判
```

### 3.2 破口

① 与 ③ 之间没有中间档。而现实中「同一枚令牌在短时间内被重复提交」非常常见：

1. **客户端超时后重试** —— 服务端已轮换并返回了新令牌，但响应在网络上丢了，
   客户端拿着旧令牌重试 → 落到 ③ → **全族吊销**
2. **两个标签页串行到达** —— 阶段 4 的前端缓解（先占位再刷新 + BroadcastChannel 广播）
   在占位机制失效时（`localStorage` 被清、另一个标签页已经开始刷）两个请求串行抵达
3. **多副本部署** —— 前端的 `inFlightRefreshes` 是模块级变量，只在单进程内有效
   （阶段 4 验收记录 §六·23 明确写了「不要扩副本数」）

### 3.3 `revokeTokenFamily` 的爆炸半径

`revokeTokenFamily(userId, triggerTokenId)` 按 **`userId`** 吊销：

```ts
this.prisma.refreshToken.updateMany({
  where: { userId, revokedAt: null },
  data: { revokedAt: now, revokedReason: REPLAY },
})
```

所以**一枚令牌的重放会踢掉该用户所有设备的登录**。这就是「商家开第二个标签页就被踢」的放大机制。

## 四、方案

### 4.1 数据模型

`refresh_tokens` 表加两列：

| 列 | 类型 | 含义 |
|---|---|---|
| `rotatedToToken` | `String?` | 本枚令牌轮换出的**新令牌密文**（AES-256-GCM）。宽限期内重放时解密后返回 |
| `graceExpiresAt` | `DateTime?` | 宽限截止时刻。**轮换时一次定死**，不因重放而延长 |

⚠️ **`RefreshToken` 不在 `TENANT_SCOPED_MODELS` 里**（它按 `userId` 索引，跨租户），
所以 `findFirst` / `updateMany` 都能用，不需要切作用域。

⚠️ **存的是密文不是明文**（决策 D1）：`token.util.ts` 里既有的原则是
「数据库里只存 sha256 摘要而不是明文……RefreshToken 表经常被备份与只读分析」。
直接写明文会与这条原则正面冲突，且**备份与流复制里的明文清理任务抹不掉**。
详见 §5.1。

### 4.2 加密与密钥派生

**密钥来源（决策 D8）**：用 **HKDF 从 `JWT_SECRET` 派生**一个独立的 32 字节密钥。

```
key = HKDF-SHA256(
  ikm  = JWT_SECRET,
  salt = 固定常量,
  info = 'refresh-token-grace-v1',
  len  = 32
)
```

用 Node 内置的 `crypto.hkdfSync`（Node 15+）。

**为什么派生而不是新增环境变量**：

- 不给部署增加一个「必须配置、漏了就启动失败」的东西（那会 breaking）
- `JWT_SECRET` 已经被 `assertSecureConfig()` 强制校验（≥ 32 字符、生产环境禁用占位符），
  派生密钥自动继承这份保护
- **职责分离**：派生出的密钥与 JWT 签名密钥不同用途，即使两者都从同一处来，
  密文与 JWT 也不能互相冒充

⚠️ **因此不需要改 `assert-secure-config.ts`**——它管的是 `JWT_SECRET`，
派生密钥自动继承那份校验。**不要**顺手加一个新的「必须配置的环境变量」，
那会让所有现有部署（含 `infra/docker-compose.yml`）启动失败。

⚠️ **代价**：`JWT_SECRET` 轮换后，旧的宽限密文解不开 → 那些令牌走超期分支 →
吊销全族。但换 `JWT_SECRET` 本来就会让所有 JWT 失效、所有人重新登录，
所以这个连带影响**不新增任何实际损失**。

**加解密**（放在 `api/src/modules/auth/token.util.ts`，与 `generateRefreshToken` / `hashRefreshToken` 并列）：

```
密文格式 = base64url( iv(12) || authTag(16) || ciphertext )

encryptToken(plain, key)   → 密文字符串
decryptToken(cipher, key)   → 明文字符串 | null（解密失败返回 null）
```

用 **AES-256-GCM**（带认证标签，能发现密文被篡改）。每次加密用**随机 iv**。

⚠️ **解密失败一律按「宽限期不可用」处理** → 走超期分支（吊销全族 + 401），
**绝不返回 null 当令牌**。这覆盖了密钥被换、密文被改、密文格式损坏三种情况。

### 4.3 判定流程

```
令牌不存在                    → 401
令牌已吊销（revokedAt 非空）：
    吊销原因是 LOGOUT          → 401（不牵连其它设备，现状不变）
    宽限期内（ROTATED 且 now < graceExpiresAt）且密文解得开
                             → 检查那枚新令牌是否还活着：
                                 还活着（未被登出、未被判重放）
                               → 返回同一枚新令牌，不吊销族   ← 新增
                                 已被明确吊销
                               → 401，不吊销族               ← 新增（见下）
    其余（超期 / 解不开 / REPLAY）→ 吊销全族 → 401
令牌未吊销：
    expiresAt 已过              → 401
    否则 → 条件更新轮换，写入宽限记录
           count === 0 → 另一个请求已轮换 → 重读 current，走同一套宽限判定
```

⚠️ **宽限期判定的前提是 `revokedReason === ROTATED`**：
一旦某枚令牌被判成真重放并吊销全族，`revokeTokenFamily` 会把它的
`revokedReason` 从 `ROTATED` 改成 `REPLAY` —— 它就不再满足宽限期条件，
族被吊销后那些密文也不该再能被返回。

⚠️ **宽限期内还要确认「那枚新令牌本身还活着」**（实施期补上，见 §5.6）。
宽限记录存的是「我轮换出了哪枚新令牌」，但**那枚新令牌可能已经被吊销了**：
- 用户用它登出（`revokedReason` 变成 `LOGOUT`）
- 它自己被判成真重放（`revokedReason` 变成 `REPLAY`）

若不检查就放行，**登出会被撤销**：用户登出后，只要有人重放它的**前身令牌**
（还在 60 秒宽限期内），就能换回一枚**有效的 accessToken** —— 登出的意图被推翻。
所以解密成功后要查一次那枚新令牌的状态：

| 那枚新令牌的状态 | 放行？ |
|---|---|
| 未吊销（活跃） | ✅ 放行 |
| `ROTATED`（它自己也轮换过，但链还活着） | ✅ 放行 —— 链式自愈依赖这个（§4.5） |
| `LOGOUT`（被登出） | ❌ 拒绝 |
| `REPLAY`（被判过重放） | ❌ 拒绝 |
| 记录已被删（用户被删等） | ❌ 拒绝 |

⚠️ **拒绝时只 401，不吊销全族**：
那枚新令牌被明确吊销，说明「终止这条链」的意图已经表达过了，
再吊销全族只会**牵连其它设备**（登出场景）或**毫无意义**（已被判重放场景）。
这与「登出后重用令牌 → 401，不牵连其它设备」是同一条原则。

⚠️ **宽限期分支不检查 `expiresAt`**：能走到这个分支说明这枚令牌刚被用过
（≤ 60 秒内轮换的），而刷新令牌的默认有效期是 30 天 —— 这个交叉在实践中不成立，
不必为它写额外的校验。

**并发竞态与「先后」竞态不再区分**（决策 D3）：两者都落进宽限期分支。

因此 **`isConcurrentRace` 方法删除**——它唯一的职责是区分这两者以决定是否吊销全族，
而这个职责已被宽限期完全取代。`requestStartedAt` 变量随之消失。

### 4.4 宽限期内返回什么

```
refreshToken = 解密(stored.rotatedToToken)   ← 同一枚
accessToken = 重新签发（signAccessToken(stored.user)）
```

**不新建 `refresh_tokens` 记录**——否则会产生令牌分叉与垃圾行。
所以 `issueTokens` 要拆成 `signAccessToken(user)` 与 `issueRefreshToken(user)` 两段。

### 4.5 链式自愈（一个重要性质）

每一枚被轮换的令牌都会拿到**自己的**宽限记录（T0→T1、T1→T2 各有一条）。
所以即便宽限期内重放 T0 返回了一枚**已被轮换**的 T1，客户端「回退」到 T1 后再刷新，
会命中 **T1 自己的**宽限记录拿回 T2 —— **自愈**。

这带来一个实现上的简化：**不需要沿着链去查「最新的有效令牌」**。
（代价是客户端可能短暂回退到一枚旧令牌，但下一次刷新会自愈。）

⚠️ 这个性质的成立依赖「客户端每次刷新都用自己当前持有的令牌」。
极端情况下（客户端持有三枚以上的陈旧令牌）可能自愈不完全，但那已经是病态场景。

### 4.6 密文的清理（决策 D6）

清理的目标有两个：**表不要无限膨胀** + **密钥轮换时受影响的行尽量少**。

⚠️ 存的是密文，所以「明文泄漏」这个最严重的风险已经不存在了（见 §5.1）。
清理从「必须做」降级为「应该做」。

**为什么不能靠惰性清理**：客户端轮换后就不会再用旧令牌，
所以绝大多数行的 `rotatedToToken` 永远等不到「有人来用它」的那一刻，
惰性清理根本不会触发。

**方案**：新建 `AUTH_QUEUE`，用项目已有的 `QueueService.addRepeating`
（BullMQ v6 的 `upsertJobScheduler`，固定 `jobSchedulerId` 保证重复注册是覆盖而非叠加）
注册一个**每小时一次**的清理任务：

```
UPDATE refresh_tokens
SET rotatedToToken = NULL
WHERE graceExpiresAt IS NOT NULL AND graceExpiresAt < now()
```

⚠️ **列名是 camelCase 不是 snake_case** —— `refresh_tokens` 只有表名被
`@@map` 映射成小写下划线，**列名保持 Prisma 的原样**
（已核实建表 SQL：`"tokenHash" TEXT NOT NULL`、`"expiresAt" TIMESTAMP(3)`）。

⚠️ **这里用的是数据库时钟，与决策 D4 的应用时钟不一致——这是有意的例外**：
清理是**批量扫描**操作，用数据库的 `now()` 可以一条 UPDATE 搞定，
不必把行捞到应用层逐条比较；而它的判定精度要求是「小时级」，
几百毫秒的时钟偏差完全无影响。**判定令牌是否在宽限期内（秒级、决定放行与否）
一律用应用时钟**，两者职责不同、不混用。

⚠️ **但实现上不能直接写原生 SQL**：`TenantPrismaService` **刻意不暴露
`$queryRaw` / `$executeRaw`**（见该类的类注释——原生 SQL 不经过租户扩展，
放开就成了绕过隔离的后门）。要用数据库时钟就调现成的 `databaseNow()`
（`SELECT now()`）拿一个时间戳，再传给 Prisma 的 `updateMany`：

```ts
const now = await this.prisma.databaseNow();
const result = await this.prisma.refreshToken.updateMany({
  where: { graceExpiresAt: { lt: now }, rotatedToToken: { not: null } },
  data: { rotatedToToken: null },
});
```

⚠️ **`RefreshToken` 不在 `TENANT_SCOPED_MODELS` 里**，所以这里的 `updateMany`
不带任何 tenantId 条件——它本来就跨租户 ✓

**兜底一**：`revokeTokenFamily` 的两个 `updateMany` 都要加 `rotatedToToken: null`——
全族吊销后，那些密文不该再能被返回。

**兜底二**：**应用启动时跑一次全量清理**。理由：清理任务依赖 BullMQ worker，
而 worker 可能没起来或挂了——那密文就会一直留着。启动时清一次，
保证「进程重启过」之后一定是干净的。成本是一条 UPDATE。

**消费端只测 service 层**：与阶段 5b 的 `RenewalWorker` 惯例一致
（`billing-renewal.e2e-spec.ts` 测的是 `RenewalService.scan()`，不是 worker 本身）。

⚠️ **本阶段只清「列」不删「行」**：`refresh_tokens` 的行在 `expiresAt` 过期后
依然留在表里（既有状况，本阶段不处理）。清理任务只把过期的 `rotatedToToken`
置 null，不删行——删行会让「令牌族」的审计线索断掉。
「过期令牌行无限累积」这个问题**如实记为遗留项**，不在本阶段解决。

## 五、关键取舍的论证

### 5.1 为什么存密文（而不是明文，也不是 HMAC 派生）

RFC 9700 要求「宽限期内应返回**同一枚**新令牌」。服务端只存令牌的 hash，
要返回同一枚，就必须能**重算出它的明文**。三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 存明文** | 轮换时把新令牌明文记在旧令牌的行上 | **与 `token.util.ts` 里既有的「不存明文」原则正面冲突**；更要命的是**清理任务抹不掉备份与流复制里的明文**——PostgreSQL 流复制 / 云厂商 PITR 的滞后可能只有几秒，那份副本里的 T1 **仍然有效**，数据库泄漏就绕过了整个宽限期机制 |
| **B. 存密文**（本设计） | 轮换时把新令牌用 AES-256-GCM 加密后记在旧令牌的行上；宽限期内解密返回 | 需要一个加密密钥（本设计用 HKDF 从 `JWT_SECRET` 派生，不新增配置项）；密钥轮换后旧密文解不开 |
| C. HMAC 确定性派生 | `T1 = HMAC(K, T0)`，服务端不存也能重算 | 要引入只有服务端知道的派生密钥；**令牌格式不再是纯随机**——`generateRefreshToken` 的生成方式、`hashRefreshToken` 的用法、以及所有依赖「令牌彼此无关」的假设都要重新审视；派生密钥自身的轮换与保管是新的长期负担 |

选 B。

**为什么不是 A**：明文落库不只是「多泄漏一点」——`token.util.ts` 的注释明确点了名
「RefreshToken 表经常被备份与只读分析」。清理任务只能抹当前主库；
**备份、WAL 归档、流复制、只读副本里的明文都抹不掉**。
若副本滞后只有几秒，它里面那枚 T1 仍可用于刷新 → 数据库泄漏直接绕过宽限期，
安全前提被完全放弃。存密文则这类副本泄露也只是泄露了密文。

**为什么不是 C**：C 在链式场景下也能自愈（服务端能顺着链重算下一枚），
但它要**改变令牌的生成方式**——从「30 字节随机数」变成「派生的确定性串」。
这会波及 `generateRefreshToken` 的语义、令牌的长度假设，
以及所有依赖「令牌彼此无关」的代码路径。B 只多加一列、**不动令牌格式**。

### 5.2 存密文之后，「服务端不存可用凭证」这个前提保住了多少

原本的原则（`token.util.ts`）：「数据库里只存 sha256 摘要而不是明文……
泄漏的只是哈希，无法反推」。

改造后 `refresh_tokens` 表里有三种数据形态：

| 列 | 形态 | 泄漏后的价值 |
|---|---|---|
| `tokenHash` | sha256 摘要 | 无（原样保留） |
| `rotatedToToken` | **AES-256-GCM 密文** | 需要密钥才能解 → 无（**前提保住**） |
| `userId` / `expiresAt` 等 | 明文元数据 | 无 |

⚠️ **保住的代价**：数据库里多了一个「用密钥就能解」的密文。
所以**密钥本身的安全性成了新的关键资产**——它与 `JWT_SECRET` 同源（HKDF 派生），
泄露 `JWT_SECRET` 意味着攻击者能伪造任意角色的 JWT，**那本来就是灾难级**，
多解出一枚宽限密文不改变量级。

⚠️ **诚实的残留风险**：派生密钥**只存在于进程内存**，不落盘、不进日志 ✓
所以「拿到密文但拿不到密钥」是常态。

### 5.2.1 密文的清理降级为「应该做」而非「必须做」

存的是密文，所以「明文泄漏」这个最严重的风险已经不存在。
清理任务现在的目的是**表不要无限膨胀** + **密钥轮换时受影响的行尽量少**，
从「必须做」降级为「应该做」。

⚠️ 但仍然要做：否则 `rotatedToToken` 列会随着每次轮换不断增长，
且密钥轮换后这些密文会永久解不开（占着空间、也拖慢备份）。

### 5.3 为什么不切分「并发」与「先后」（决策 D3 的实测依据）

原设想：并发竞态仍拒（401），只有「先后」竞态走宽限期（200），理由是「行为变化面最小」。

**实测推翻了这个切分**。在 `refresh()` 入口打临时探针日志，跑现有的并发用例：

```
[PROBE-REFRESH]  068cb5b4  ...813814   ← 请求 A 进入
[PROBE-REFRESH]  068cb5b4  ...813821   ← 请求 B 进入（晚 7ms）
[PROBE-ROTATE-OK] 068cb5b4  ...813829   ← A 完成轮换（比 B 进入还晚 8ms）
```

B 进入时 A 还没写轮换记录，于是 `revokedAt(829) >= requestStartedAt(821)` → 判真并发 → 401。
连跑 5 次，B 都在 A 完成轮换**之前**进入，间隔稳定在 6–9ms。

**问题**：这 7ms 的窗口是**偶然的**。现有测试断言 `[200, 401]`，
一旦在别的机器或 CI 上两个请求**真串行**抵达，第二个请求的 `requestStartedAt`
就会晚于 A 的 `revokedAt` → 判「先后」→ 宽限期 → **200** → 断言从 `[200, 401]`
变成 `[200, 200]` 而挂。

**等于把一个稳定测试改成 flaky 测试。** 所以宽限期必须**统一处理**两者，
判定不再依赖任何时序。

⚠️ 探针日志已在核实后移除，`auth.service.ts` 恢复原状。

### 5.4 并发路径的原子性保证

B 的条件更新 `count === 0` 意味着 A 的那次 `updateMany` 已经完成。
而 A 的那一次 `updateMany` **一次性原子地写了三列**
（`revokedAt` / `rotatedToToken` / `graceExpiresAt`），
所以 B 重读 `current` 时**必然拿得到** `rotatedToToken`。

⚠️ 实测还发现：并发时 B 走的是 `stored.revokedAt` 分支而不是 `rotated.count === 0` 分支
（探针日志里没有出现 `ROTATE-LOST`）——但那也是时序决定的，**两条路径都必须支持宽限期**。

### 5.5 行为变更（必须如实记录）

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 轮换后 **60 秒内**串行重用旧令牌 | 判真重放 → **吊销全族** | 返回同一枚新令牌，**不吊销** |
| 轮换后 60 秒内**并发**重用旧令牌 | 401（只拒本请求） | 返回同一枚新令牌 |
| 轮换后 **超过 60 秒**重用旧令牌 | 判真重放 → 吊销全族 | 判真重放 → 吊销全族（**不变**） |
| 登出后重用令牌 | 401，不牵连其它设备 | 不变 |
| **登出后重用它的「前身令牌」**（宽限期内） | 401（ROTATED 无宽限期） | **401，不牵连其它设备**（实施期补上，见 §5.6） |
| **全族吊销后重用族内已轮换的令牌** | 401 | **401**（实施期补上，见 §5.6） |
| 宽限密文解不开（密钥换了 / 密文被改） | —— 无此场景 | 走超期分支 → 吊销全族 + 401（**绝不返回 null 当令牌**） |

第一条正是本阶段要修的。第二条是决策 D3 的直接后果——
「并发竞态」不再是一个独立的安全档位，被合并进了宽限期。

**安全影响评估**：宽限期内同一枚令牌可以被无限次兑换成**同一枚**新令牌。
攻击者第一次就能换到它，重复兑换**没有额外收益** ✓

**对前端的影响**：前端拿到的不再是「401 → 需要重新登录」，
而是「200 + 同一枚新令牌」。所以前端的重试逻辑从「失败就重新登录」
变成「拿到 200 就继续用」——**这正是我们要的**：
网络抖动不再把用户踢下线。

### 5.6 实施期补上的两个洞：ROTATED 行的宽限密文

**背景**：宽限记录是**阶段 5c 才引入**的。改造前，`ROTATED` 状态的一行
**没有任何可兑换的秘密**（旧令牌已作废、库里只有 sha256 摘要），
所以「它还带着 ROTATED 这个原因」无关紧要。

阶段 5c 之后，`ROTATED` 行上多了一枚**可兑换的新令牌密文**。
于是两个**改造前不可利用**的既有缺口，变成了可利用的漏洞。

#### 洞一：家族吊销够不到已轮换的兄弟行

`revokeTokenFamily` 的第一个 `updateMany` 的 where 是
`{ userId, revokedAt: null }` —— 只覆盖**还没被吊销**的行。
已经 `ROTATED` 的行 `revokedAt` 非空，被直接跳过。

结果：全族吊销之后，族内那些**已轮换**的行仍然带着
`revokedReason = ROTATED` + 完整的宽限密文 + 未到期的 `graceExpiresAt`
—— 重放它们照样进宽限期分支。

**后果**：拿回一枚**已经被吊销**的令牌。危害有限（那枚令牌本身已死，
拿去用只会 401），但「吊销全族」名不副实，且客户端会以为刷新成功了。

**修法**：第一个 `updateMany` 的 where 加上
`OR: [{ revokedReason: ROTATED }]`，让已轮换的行也被改写成 `REPLAY`。
⚠️ **`LOGOUT` 不纳入** —— 登出的令牌不该被重放路径改写成 `REPLAY`，
那会掩盖「用户主动登出」这个事实。
⚠️ 这个修改**不会牵连其它设备**：它只在「真重放被判定」时生效，
而那时整个令牌族本来就要死。

#### 洞二：登出后，前身令牌仍能换回一枚有效的 accessToken

`logout` 只吊销了**被提交的那一枚**。它的**前身**（把轮换成它的那枚）
仍然是 `ROTATED`，密文完好，宽限期未到。

结果：用户登出之后，只要有人重放**前身令牌**，
`handleRevokedToken` 的宽限期分支照样返回 200 + 一枚**新签发的 accessToken**
—— **登出的意图被撤销了**。

⚠️ 这是本阶段引入的**真漏洞**：改造前重放前身令牌必然 401。

**修法**：见 §4.3 —— 宽限期内放行之前，先确认**那枚新令牌本身还活着**。
若它已被 `LOGOUT`（登出）或 `REPLAY`（判过重放）明确吊销，则
**只 401，不吊销全族**。

⚠️ **注意 `ROTATED` 的目标要放行**：链式自愈（§4.5）依赖
「重放 T0 拿回 T1，而 T1 此时已经是 ROTATED」——
若把 `ROTATED` 也当拒绝，链就断了。

**共同的教训**：`revokedReason` 从「一个原因标记」变成了
「决定这条链是否还活着的状态机」。凡是判断「这枚令牌还能不能用」的地方，
都不能只看宽限期，**必须看它指向的那枚令牌**。

## 六、前端配套

### 6.1 抽出可测的决策模块

`makeJwtCallback` **已经是纯函数**（不依赖 next-auth），只是没导出，
且与 `NextAuth({...})` 住在同一个文件里——而 `auth.ts` 顶层就调 `NextAuth({...})`，
import 它会初始化 next-auth 的整个依赖图（含 `server-only`），在 Vitest 的 node 环境里
直接报 `Cannot find module 'next/server'`。

**方案**：把 `makeJwtCallback` 与 `session` 回调抽到 `@/lib/jwt-callback.ts`，
`auth.ts` 引用它。

⚠️ **不需要搭 jsdom 基建**——纯模块在 node 环境就能测。
（merchant-admin 的 jsdom 组件测试基建属于阶段 5d。）

⚠️ **抽出来的模块不能 import `next-auth` 的任何东西**（连类型也不能）：
`import type` 虽然编译后会被擦除，但一旦写成普通的 `import`，
Vitest 就会去解析 next-auth 的依赖图 → 同样的 `Cannot find module 'next/server'`。
所以 `jwt-callback.ts` 里**自己定义最小类型**：

```ts
export interface JwtToken {
  accessToken?: string;
  refreshToken?: string;
  role?: string;
  tenantId?: string | null;
}
export interface SessionLike {
  accessToken: string;
  role: string;
  tenantId: string | null;
}
```

`auth.ts` 那边把 next-auth 的回调参数**适配**成这两个类型即可。

⚠️ **副本约定**：`storefront/src/lib/jwt-callback.ts` 与
`merchant-admin/src/lib/jwt-callback.ts` 是**两份副本**，与既有的
`token-refresh.ts` / `token-expiry.ts` 副本约定一致，两份**逐行一致**。

⚠️ **「链式自愈」这条必须走满 4 步**，只走 2 步测不到 §4.5 那个性质：

② 用 T1 刷新                    → 得到 T2（T1 标 ROTATED，写宽限记录）★ T1 此时已作废

④ 用 ③ 拿到的 T1 再刷新         → 200，且得到 T2（命中 T1 自己的宽限记录）★ 自愈

## 八、风险清单

### 8.1 可被利用的漏洞

| 风险 | 评估 |
|---|---|
| 攻击者拿到泄漏的令牌，在 60 秒内反复兑换 | **无额外收益**——第一次就换到了同一枚令牌 |
| 宽限密文在库里残留 | **无直接危害**——没有派生密钥解不开。见 §5.2 |
| 宽限期让「重放检测」失效 | **不失效**——60 秒后仍然吊销全族 |
| 并发竞态不再被单独识别 | 合并进宽限期，见 §5.5 |
| **登出后重放前身令牌能换回有效 accessToken** | **已修**——宽限期内放行前先确认目标令牌还活着（§5.6 洞二） |
| **全族吊销后重放族内已轮换的令牌** | **已修**——`revokeTokenFamily` 的 where 覆盖 ROTATED 行（§5.6 洞一） |
| 宽限期判定用应用时钟，与阶段 5a 的 `databaseNow()` 约定不一致 | 多副本时钟偏差会让宽限期长度有秒级浮动。**刻意为之**（决策 D4，同段逻辑不混用时钟源），在代码注释与验收记录里如实标注 |

### 8.2 正确性风险

| 风险 | 缓解 |
|---|---|
| 宽限期判定用错时钟 | 与同文件的 `revokedAt` / `expiresAt` 一致（决策 D4） |
| `rotated.count === 0` 分支漏掉宽限期 | 两条路径都实现（§5.4） |
| 客户端持有陈旧令牌导致自愈不完全 | 病态场景，见 §4.5 |
| 密文清理任务在多副本下重复执行 | 幂等（都是置 null） |
